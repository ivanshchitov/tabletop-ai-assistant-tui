# Tabletop AI Assistant

Консольный TUI-ассистент по настольным играм. Отвечает на вопросы о правилах, спорных ситуациях, стратегиях и рекомендациях по настольным играм с помощью модели, выбранной командой `/models` (по умолчанию `deepseek-v4-flash`), а вопросы не по теме вежливо отклоняет с объяснением причины. Ответы рендерятся как Markdown с эффектом постепенной печати, история диалога сохраняется между запусками.

## Технические требования

- Python 3.9+
- Зависимости из `requirements.txt`: `rich`, `requests`, `python-dotenv`
- API-ключ в переменной окружения `OPENCODE_API_KEY` (задаётся в `.env`, см. `.env.example`) — используется для доступа к выбранной модели через эндпоинт OpenCode Zen `https://opencode.ai/zen/v1/chat/completions`
- Терминал с поддержкой ANSI-цветов и Unicode/emoji
- Интернет-соединение для обращения к API

Установка зависимостей и запуск:

```bash
pip install -r requirements.txt
echo "OPENCODE_API_KEY=sk-ваш_ключ" > .env
python tabletop-ai-assistant.py
```

Команды приложения (с автодополнением по Tab):

- `/exit` — выход; история сохраняется в `history.json` сразу после каждого ответа, поэтому
  при следующем запуске контекст диалога восстанавливается, и агент продолжает беседу
  с учётом прошлых обменов.
- `/commands` — панель всех команд с краткими описаниями: `↑`/`↓` — выбор,
  `Enter` — выполнить выбранную команду прямо из панели, `Esc` — отмена.
  В статус-баре приложения подсказка показывает только `/exit` и `/commands`.
- `/settings` — экран настроек ответа и контекста: `↑`/`↓` — выбор поля, `←`/`→` —
  формат ответа (`compact` / `json` / `free`) и стратегия управления контекстом
  (`резюме` / `окно` / `факты` / `ветки`), цифры и `Backspace` — редактирование числовых полей:
  максимальный объём ответа в словах (10..1000), лимит вариантов в списке-подборке
  (1..10, например «предложи список настольных игр»), температура запроса (0.0..2.0,
  не более одного знака после точки — второй знак в поле ввести невозможно),
  порог сжатия контекста в сообщениях (5..50, только целое; для стратегии окна — это же
  значение задаёт размер окна) и потолок токенов собираемого запроса сессии
  (5000..50000, только целое), `Esc` — сохранить и выйти.
- `/models` — панель выбора модели: `↑`/`↓` — выбор, `Enter` — применить, `Esc` — отмена.
  Фиксированный список: `deepseek-v4-flash`, `deepseek-v4-pro`, `kimi-k2.5`, `glm-5.1`,
  `mimo-v2.5-free`, `kimi-k2.6`, `kimi-k3`. Курсор стартует на текущей модели, и она
  помечена «(текущая)»; выбор действует до конца сессии, после перезапуска снова активна
  модель по умолчанию. Под каждым ответом модели выводится строка с временем ответа,
  количеством токенов и стоимостью запроса — только на экран, в `history.json` не сохраняется.
  Если модель
  упёрлась в бюджет `max_tokens` (`finish_reason=length`), над строкой метрик появляется
  предупреждение: ответ мог быть обрезан, а при пустом ответе — что модель исчерпала бюджет
  и ответ не сгенерирован.
- `/usage` — отчёт по токенам без обращения к модели: метрики последнего запроса, итоги
  сессии (число запросов, входные/выходные/суммарные токены, стоимость) и расход всей
  сохранённой истории (сумма по записям `history.json`).
- `/context` — состояние контекста без обращения к модели: активная стратегия, размер окна
  и потолок токенов, число ходов в ближайшем запросе, память стратегии (охват резюме,
  пары блока фактов, ветки диалога) и приближённая оценка токенов запроса против потолка
  (помечена «≈»). Отчёт строится из снимка, который отдаёт агент.
- `/branches` — ветки диалога: `↑`/`↓` — выбор, `Enter` — сделать ветку активной,
  `c` — поставить чекпоинт в текущей позиции, `n` — создать ветку от чекпоинта, `Esc` — закрыть.
  Панель не делает запросов к модели. Ветки живут в пределах сессии; в `history.json`
  попадают обмены всех веток плоским списком.
- `/memory` — память агента: без аргументов печатает отчёт по трём слоям (что лежит в каждом,
  в каком хранилище, сколько живёт) и перечень правил маршрутизации; с аргументами управляет
  слоями: `/memory goal <цель задачи>` пишет в рабочую память, `/memory remember <сведение
  о вас>` — в долговременную, `/memory forget <ключ>` удаляет одну запись, `/memory forget all`
  очищает рабочую и долговременную память, не трогая текущий диалог. Запросов к модели
  команда не делает.
- `/profile` — профиль пользователя (персонализация): без аргументов печатает отчёт —
  активный профиль с его разделами, все профили файла `profile.json` и срок жизни профиля;
  `/profile setup` запускает диалог настройки из пяти вопросов (имя, стиль, ограничения, опыт,
  любимые жанры), `/profile use <имя>` переключает активный профиль, `/profile forget <имя>`
  удаляет его. Запросов к модели команда не делает.

### Персонализация: профиль пользователя

Поверх слоёв памяти живёт профиль — предпочтения, которые вы задаёте сами. Профиль отвечает на
вопрос «как отвечать этому человеку», а не «что известно»: он уходит модели отдельным системным
сообщением сразу после системного промпта настроек и выше памяти, поэтому действует при любой
стратегии контекста, и в каждом вопросе — повторять предпочтения в тексте вопроса не нужно.

Профиль состоит из имени и четырёх разделов:

| Раздел | Что задаёт |
|---|---|
| Стиль | насколько подробно и каким тоном отвечать |
| Ограничения | что не предлагать и чему следовать: время партии, сложность, состав |
| Опыт | насколько вы знакомы с настольными играми |
| Жанры и механики | что вы любите: евро, амери-трэш, построение движка, кубомёт |

Настройка — диалог «вопрос — ответ» (`/profile setup`): приложение задаёт вопросы по одному и
записывает ответ в свой раздел. `Enter` на вопросе оставляет раздел как был (у нового профиля —
пустым), `Ctrl+C` отменяет настройку, ничего не записывая. Настроенный профиль становится
активным; повторная настройка под тем же именем заменяет отвеченные разделы.

Активный профиль виден в статус-баре после каждого шага — рядом с моделью и стратегией, как и
остальное состояние сессии; без профиля строки о нём в статус-баре нет.

Профили лежат в отдельном файле `profile.json` (`TABLETOP_PROFILE_FILE`): в нём может быть
несколько профилей, один из них активный — так один и тот же вопрос можно задать под разными
профилями и получить разные ответы. `/clear` профиль не трогает: он не часть диалога. Снять
профиль можно командой `/profile forget <имя>`.

Профиль уступает настройкам приложения: формат ответа, объём и лимит списка задаёт `/settings`,
а профиль влияет на подачу в этих границах — иначе предпочтение «отвечай просто текстом» ломало
бы, например, формат `json`.

### Слои памяти агента

Память разделена на три слоя с разным содержимым, сроком жизни и хранилищем:

| Слой | Что в нём | Жизнь | Хранилище |
|---|---|---|---|
| Краткосрочная | ходы текущего диалога дословно | текущий диалог, очищается `/clear` | `history.json`, блок `dialogues` |
| Рабочая | цель задачи и ограничения (+ память активной стратегии: резюме, факты, ветки) | текущая задача, очищается `/clear` | `history.json`, блок `working` |
| Долговременная | сведения о вас: профиль, принятые решения, знания о вашей группе | между сессиями, `/clear` не трогает | `memory.json` |

Что и куда попадает, решает правило маршрутизации по оборотам реплики — без запросов к модели:
«я опытный игрок», «я не люблю», «моя группа» → долговременная память (профиль);
«решили», «запомнили», «впредь» → долговременная память (решения); «в нашей компании принято» →
долговременная память (знания); «хочу», «подбери», «собери», «посоветуй» → рабочая память (цель);
«не предлагай», «бюджет», «до N ₽», «N человек», «без таймера» → рабочая память (ограничения).
Полный перечень печатает `/memory`. Каждая запись видна в журнале после ответа строкой вида
`Память: долговременная (профиль: опыт), рабочая (цель)`.

Слои уходят в запрос отдельным системным сообщением выше ходов диалога: долговременная память
идёт перед рабочей, а свежая реплика остаётся последней — если она противоречит памяти, агент
следует реплике. Пустые слои сообщения не добавляют, поэтому на пустой памяти форма запроса
не меняется. Записи долговременного слоя переживают перезапуск и `/clear`; снять их можно
командой `/memory forget all`.

### Стратегии управления контекстом

Стратегия выбирается на экране `/settings` и действует со следующего вопроса. Стек ходов
сессии пополняется всегда и никогда не очищается стратегией — стратегия решает лишь, что из
него попадёт в запрос, поэтому переключение ничего не теряет.

| Стратегия | Что уходит в запрос | Доп. запросы к модели | Память |
|---|---|---|---|
| `резюме` (по умолчанию) | system + резюме старых обменов + неотжатый хвост | суммаризатор при достижении порога/потолка | резюме и число покрытых обменов |
| `окно` | system + последние N сообщений | нет | нет |
| `факты` | system + блок фактов «ключ — значение» + последние N сообщений | извлекатель фактов перед каждым вопросом | блок фактов |
| `ветки` | system + ходы активной ветки | нет | ветки и чекпоинт (сессия) |

- **Резюме**: ходы идут дословно, пока их не больше порога; при достижении порога (или при
  превышении потолка токенов) агент сворачивает старейшие ходы (кроме последнего обмена)
  моделью в резюме и подставляет его в запрос вместо них. Свёрнутые ходы остаются в стеке.
  В журнале при сжатии индикатор показывает «Суммаризация...», а после ответа появляется
  строка «Контекст сжат: N сообщений (M обменов) → резюме».
- **Окно**: в запрос уходят только последние N сообщений (целыми обменами, последний обмен
  всегда), суммаризатор не вызывается вовсе.
- **Факты**: перед каждым вопросом агент отдельным запросом просит модель обновить блок
  фактов (цель, ограничения, предпочтения, решения, договорённости) и получает его как
  JSON-объект пар «ключ — значение»; значение существующего ключа заменяется, число ключей
  ограничено. Сбой извлекателя не отменяет ответ: вопрос уходит с прежним блоком, а
  сообщение остаётся в очереди до следующего обновления — в журнале видно строку
  «Факты не обновлены». При успехе печатается «Факты обновлены: N ключей».
- **Ветки**: чекпоинт отмечает позицию в активной ветке, новая ветка начинается копией ходов
  до этого места и дальше развивается независимо; в запрос уходят ходы активной ветки.

Резюме и блок фактов хранятся в `history.json` и восстанавливаются при рестарте; ветки
переживают только сессию. Файл истории хранит все обмены дословно.

## Структура проекта

```
tabletop-ai-assistant.py  # Точка входа: python tabletop-ai-assistant.py
core/                      # Настройки, промпты, API-клиент, история — без rich/терминала
  config.py                 # Переменные окружения, константы (порог/потолок сжатия, стратегии, лимиты блока фактов и памяти)
  answer_settings.py         # AnswerFormat, ContextStrategy, AnswerSettings — формат/объём/лимит/температура + порог сжатия, потолок контекста, стратегия
  context_compressor.py      # Чистая логика сжатия: порог, разделение хода, сборка запроса и промпта суммаризатора
  context_strategies.py       # Чистая логика стратегий: окно сообщений, блок фактов (слияние, разбор JSON), ветки с чекпоинтом
  memory_layers.py             # Слои памяти агента: правила маршрутизации реплик по слоям, сообщение памяти для запроса, описание правил
  long_term_memory.py           # Долговременная память агента (memory.json): записи с категориями, чтение, немедленная запись
  user_profile.py                # Профиль пользователя (profile.json): разделы предпочтений, несколько профилей с активным,
                                 #  скрипт диалога настройки «вопрос — ответ», сообщение профиля для запроса
  prompts.py                  # Сборка системного и user-промпта из assets/
  api_client.py                # APIClient — запросы к API массивом сообщений, retry с backoff, ask_with_usage (время/токены/стоимость)
  usage.py                      # estimate_cost, estimate_tokens, SessionLedger — стоимость, оценка токенов, накопитель сессии
  tabletop_agent.py             # TabletopAgent — агент: конфиг (настройки/модель/стратегия),
                                 #  стек ходов сессии (append-only) и память стратегии (резюме, факты, ветки),
                                 #  слои памяти (краткосрочная — лог, рабочая — конверт истории, долговременная — свой файл),
                                 #  маршрутизация реплик по слоям, автовосстановление контекста при создании,
                                 #  профиль персонализации (сборка из ответов диалога, снимок profile_report),
                                 #  снимки контекста (context_report) и памяти (memory_report),
                                 #  метрики последнего запроса (last_result), сжатия (last_compression) и обновления фактов (last_facts)
  history_manager.py           # Долговременное хранилище диалога (history.json): конверт с резюме, фактами и рабочей памятью,
                                 #  чтение, немедленная запись, без вытеснения
ui/                         # Терминальный интерфейс
  tui_app.py                  # Основной класс TabletopAITUI: rich-интерфейс, /commands, /settings, /models, /context, /memory, /profile, /branches
  commands_screen.py           # Редьюсер панели команд /commands (без привязки к терминалу)
  settings_screen.py           # Логика экрана /settings (без привязки к терминалу)
  branches_screen.py             # Редьюсер панели веток /branches
  models_screen.py               # Редьюсер панели выбора модели /models
  keyboard.py                  # Чтение клавиш для экранов /commands, /settings, /branches и /models
tests/                      # Тесты
  unit/                       # Быстрый слой: логика core/, редуктор настроек, главный цикл
  e2e/                        # Приложение целиком в псевдотерминале против stub-сервера
assets/                    # system_prompt.md, answer_format_*.md, summary_prompt.md, facts_prompt.md, memory_prompt.md, profile_prompt.md
openspec/                  # Спецификации и активные изменения (OpenSpec)
.claude/                   # Команды и скиллы /opsx:* для Claude Code
.opencode/                 # Те же команды и скиллы /opsx-* для OpenCode
history.json               # Сохранённая история и рабочая память (в .gitignore)
memory.json                # Долговременная память агента (в .gitignore)
profile.json               # Профили пользователя (в .gitignore)
.env                       # OPENCODE_API_KEY=sk-... (в .gitignore)
```

Переменные окружения (`.env` или оболочка): `OPENCODE_API_KEY`, `OPENCODE_API_URL`,
`TABLETOP_HISTORY_FILE`, `TABLETOP_MEMORY_FILE` (файл долговременной памяти, по умолчанию
`memory.json`), `TABLETOP_PROFILE_FILE` (файл профилей пользователя, по умолчанию
`profile.json`), `TABLETOP_REQUEST_TIMEOUT`, `TABLETOP_TYPING_DELAY`,
`TABLETOP_COMPRESS_AFTER` (порог сжатия по умолчанию, сообщений, дефолт 10) и
`TABLETOP_MAX_SESSION_TOKENS` (потолок контекста по умолчанию, токенов, дефолт 20000).
Порог и потолок живут настройками сессии (`/settings`), переменные задают их значения
по умолчанию — в первую очередь для e2e-прогонов и демо.

## Сценарии использования

- **Правила игры**: «Подскажи правила игры "Каркассон"» — получить структурированное описание подготовки, хода и подсчёта очков.
- **Спорная ситуация за столом**: «Можно ли ставить мипла на монастырь, если он уже занят?» — разрешение спорного момента со ссылкой на логику правил.
- **Подбор игры**: «Что купить на 4 игроков для вечеринки?» — рекомендация с уточнением количества игроков, сложности и жанра.
- **История и контекст игры**: «Откуда взялась игра "Диксит"?» — краткая справка по происхождению и особенностям игры.
- **Вопрос не по теме**: «Какая сегодня погода?» — ассистент объясняет, что работает только с настольными играми, и предлагает переформулировать вопрос.
- **Панель команд**: `/commands` — посмотреть все команды с описаниями и выполнить нужную, не набирая её вручную.
- **Смена модели**: `/models` — переключиться на другую модель из списка и дальше задавать вопросы ей; модель видна в статус-баре.
- **Управление контекстом**: `/settings` — переключить стратегию (`резюме` / `окно` / `факты` / `ветки`)
  и сравнить, как меняются ответы и расход токенов на одном и том же диалоге.
- **Ветки диалога**: `/branches` — поставить чекпоинт, создать ветку от него, продолжить
  диалог в каждой ветке независимо и переключаться между ними.
- **Учёт токенов**: статус-бар после каждого шага показывает расход текущей сессии
  (суммарные токены и стоимость), `/usage` даёт развёрнутый отчёт по токенам, а `/context` —
  состояние контекста: стратегию, память и оценку запроса против потолка.
- **Память между сессиями**: `/memory` — посмотреть, что агент помнит в каждом слое (ход
  текущего диалога, задача этого разговора, сведения о вас), дописать цель задачи
  (`/memory goal`), сведение о себе (`/memory remember`) или снять записи (`/memory forget`).
  Сведения о вас переживают перезапуск и `/clear` — в отличие от диалога и задачи.
- **Персонализация**: `/profile setup` — пройти диалог настройки и получить ответы под себя
  (проще, короче, без игр с таймером), `/profile use <имя>` — переключаться между профилями
  и сравнивать ответы на один и тот же вопрос. Профиль виден в отчёте `/profile` и действует
  в каждом запросе, хотя в самом вопросе о предпочтениях не сказано ни слова.

## Тесты

```bash
pip install -r requirements-dev.txt

pytest                # весь набор, кроме обращений к настоящему API
pytest tests/unit -q  # быстрый слой, около секунды
pytest tests/e2e -q   # сценарии в псевдотерминале, около минуты
```

Тесты разделены на два слоя.

**Юнит-тесты** (`tests/unit/`) проверяют логику без терминала: валидацию настроек, сборку
промптов, чистую логику стратегий (окно, блок фактов, ветки), правила маршрутизации памяти по
слоям и её хранилище, работу агента по каждой стратегии, работу с историей, разбор ответов API
и ретраи, редьюсеры панелей, а также главный цикл приложения с подставленными консолью,
историей и клиентом. Отдельный файл `test_keyboard.py` работает с
настоящим псевдотерминалом — иначе код перевода терминала в cbreak-режим просто не выполняется.

**Сценарные тесты** (`tests/e2e/`) запускают настоящее приложение в псевдотерминале и общаются
с ним так же, как человек: задают вопросы, ходят по экрану `/settings` стрелками, нажимают
Ctrl+C, перезапускают приложение и проверяют, что история подхватилась. Вывод пропускается через
эмулятор терминала `pyte`, поэтому проверки смотрят на отрисованный экран, а не на поток
управляющих последовательностей. Вместо OpenCode Zen отвечает локальный stub-сервер, который
заодно записывает все запросы — это позволяет проверить, что именно ушло в API при выбранных
настройках.

Отдельный набор (`tests/e2e/test_live_api.py`) запускает приложение против **настоящего**
OpenCode Zen — без заглушки, с реальным ключом из `.env`:

```bash
pytest tests/e2e/test_live_api.py -m network -q
```

Чтобы видеть, что происходит на экране приложения во время прогона:

```bash
pytest -s --show-tui=live tests/e2e/test_live_api.py -m network -q     # трансляция по ходу работы
pytest -s --show-tui=screen tests/e2e/test_live_api.py -m network -q   # итоговый экран после теста
```

Режим `live` выводит поток приложения как есть — с перерисовками, спиннером и цветом, будто вы
сидите за настоящим сеансом. Режим `screen` печатает только итоговый экран, его удобно
перенаправлять в файл. Флаг `-s` обязателен: иначе pytest перехватит вывод.

Эти тесты проверяют не механику приложения, а то, слушается ли модель собранного промпта:
возвращает ли она точную фразу отказа на посторонний вопрос, соблюдает ли выбранный формат
(в том числе когда вопрос просит ответить иначе), укладывается ли в заданные лимиты объёма и
количества вариантов. Проверки намеренно нестрогие — ответы модели недетерминированы. Набор
помечен маркером `network` и в обычный прогон не попадает; без ключа он пропускается.

Ответы настоящей модели можно записать один раз и дальше проигрывать локально:

```bash
pytest tests/e2e/test_recorded_answers.py -m network --record-cassettes
```

Для этого нужен настоящий `OPENCODE_API_KEY`; без записанных кассет соответствующие тесты
пропускаются.

## Разработка через OpenSpec

Изменения, затрагивающие поведение приложения (новая команда, новая настройка, другая логика
промптов или форматов), делаются через [OpenSpec](https://github.com/Fission-AI/OpenSpec):
сначала спецификация, потом код. Мелкие правки вроде опечатки этого не требуют.

```bash
npm i -g @fission-ai/openspec   # CLI нужен на PATH: команды агентов вызывают его напрямую
openspec list                   # активные изменения
```

Цикл работы — это набор слэш-команд агента. Подключены два агента, оба работают с одним и тем же
каталогом `openspec/`: **Claude Code** (файлы в `.claude/`, команды через двоеточие) и **OpenCode**
(файлы в `.opencode/`, те же команды через дефис).

| Claude Code | OpenCode | Что делает |
| --- | --- | --- |
| `/opsx:explore` | `/opsx-explore` | Обсудить идею и прояснить требования до того, как что-то писать. |
| `/opsx:propose "…"` | `/opsx-propose "…"` | Создать `openspec/changes/<id>/` с `proposal.md`, дельта-спеками, `design.md` и `tasks.md`. Код при этом не трогается. |
| `/opsx:update` | `/opsx-update` | Пересобрать артефакты изменения после новых решений. |
| `/opsx:apply` | `/opsx-apply` | Реализовать изменение по задачам из `tasks.md`. |
| `/opsx:archive` | `/opsx-archive` | Влить дельта-спеки в основные спеки `openspec/specs/` и закрыть изменение. |
| `/opsx:sync` | `/opsx-sync` | То же вливание, но без закрытия изменения. |

Скилл `.claude/skills/feature-builder/` (и его копия `.opencode/skills/feature-builder/`) написан
вручную и при перегенерации не теряется. Срабатывает на «создай фичу» / «new feature» и проводит
фичу через весь цикл: `/opsx:propose` без кода (план — `tasks.md` изменения) → ветка по имени
изменения → `/opsx:apply` с TDD по задачам (падающий тест → минимальный код → `pytest`) →
финальный `pytest`, `/opsx:archive`, обновление `CLAUDE.md`/`README.md`, fast-forward-слияние в
`main`. Каждая мутация git — только после подтверждения. Общается в стиле caveman — короткие
статусы, без пересказа кода. Скилл `solve-challenge-task` (там же) оборачивает его для задания
дня челленджа: разбор задачи и сценарий демо → фича через `feature-builder` → запись экрана
`scripts/record_screen.sh` → черновик README дня в `videos/` (не попадает в git).

Файлы агентов сгенерированы и правятся не вручную, а перегенерацией:

```bash
openspec init --tools claude     # обновить .claude/
openspec init --tools opencode   # обновить .opencode/
```

Структура каталога:

```
openspec/
  config.yaml     # Схема (spec-driven) и язык артефактов — русский
  specs/          # Основные спецификации; пишутся только archive/sync, вручную не правятся
  changes/        # Активные изменения: по папке на каждое
```

Дельта-спек в изменении — это описание разницы с основной спецификацией, а не её копия.

`openspec/specs/` уже содержит основную спецификацию проекта — возможности, зафиксированные
реверс-инжинирингом действующего кода: `question-answering`, `answer-settings`,
`api-integration`, `history-persistence`, `terminal-ui`, `settings-screen`, `configuration`,
`context-strategies`, `test-infrastructure` и `model-selection`. Она — эталон для будущих
`MODIFIED`-дельт.
