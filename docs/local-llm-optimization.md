# День 29. Оптимизация локальной LLM

Оптимизация здесь — ограничение ресурсов и предметный prompt для коротких ответов. Это демонстрационное сравнение установленных локальных моделей; предельная фактическая точность не является целью. Неверные ответы сохранены и оценены по смыслу.

## Что изменилось

`/local` показывает параметры основного ответа Qwen3.5-2B. `/local baseline|optimized` переключает режим, сохраняя Q4_K_M или Q4_K_XL.

| Параметр | Исходный профиль | Оптимизированный кандидат |
|---|---|---|
| Temperature | Настройка сессии; в замере 0.7 | 0.3 |
| Max tokens | Прежняя политика; в замере 2000 | 1024 |
| Окно сервера | 32000 | 8192 |
| Reasoning | auto, budget 256 | auto, budget 256 |
| Базовый prompt | Общий | Короткий, для правил/подсчёта/уточнений |

Оптимизированная температура имеет приоритет над `/settings`; формат, объём, пользовательский профиль, память, инварианты и RAG сохраняются. Параметры вспомогательных запросов не изменяются. Исходный профиль доступен для длинных бесед. INI необходимо перечитать перезапуском сервера. `/local` показывает политику приложения, а не запрашивает работающий сервер; benchmark отдельно проверяет фактическое окно через `/props`.

Три варианта последовательно: исходный Q4_K_M → оптимизированный Q4_K_M → оптимизированный Q4_K_XL. Три одинаковых вопроса, один общий seed=42, свободный формат, max_words=70. Критерии записаны до генерации; правильные ответы не подставлялись в prompt. Перед каждым вопросом новое состояние настоящего агента, RAG и автоматические инструменты выключены, cache_prompt=false. Сервер отдельный, offline, свободный порт; пользовательский сервер не останавливался. Полные тесты параллельно не выполнялись. Приложения пользователя и фоновые процессы ОС продолжали работать; фоновая нагрузка не исключалась.

Прогрев отдельным коротким запросом не входит в таблицу времени вопросов. Время ответа — сумма длительностей успешных HTTP-запросов, включая возможные повторы проверки инвариантов; в JSON также есть полное wall_seconds. Таймауты и другие API-ошибки не входят в медиану HTTP-времени и токены/с: их wall_seconds и error сохраняются отдельно. Не сравнивайте медиану без количества ошибок. Таймаут 600 с, одна попытка HTTP; повторы проверки инвариантов выполняются агентом отдельно. Токены/с — сумма completion_tokens / сумма HTTP-времени: включает prefill и рассуждения, не является чистой скоростью декодирования. В JSON доступны исходные ответы и сообщения, finish_reason, фактические параметры, путь/размер GGUF и настройки загруженного сервера.

Сравнение качества и скорости сокращено до первых трёх вопросов по указанию пользователя. Готовые ответы переиспользованы без новой генерации. Для Q4_K_XL первый ответ получен до остановки расширенного прогона, два следующих — после перезапуска сервера с теми же настройками. Дополнительный прогрев не входит во время ответа и записан в restart_measurements.

RSS исходного и оптимизированного Q4_K_M охватывает первоначальные сессии из шести вопросов; RSS Q4_K_XL — максимум двух сокращённых сессий, включая прерванную генерацию при остановке. Эти пики приведены справочно: строгий вывод о разнице RSS квантований на трёх вопросах по ним сделать нельзя.

RSS — максимум суммы резидентной памяти собственной группы процессов (router и его модель), выборка раз в 0.2 с; прогрев и основные вопросы отмечены отдельно. Это не вся память устройства, не энергия, не точная величина пиков между выборками. GGUF в таблице — файл языковой модели; размер не включает отдельный мультимодальный проектор.

## Выводы и ограничения

На трёх выбранных вопросах при переходе исходный M → оптимизированный M медиана HTTP-времени изменилась с 302.70 до 108.53 с; справочный выборочный пик RSS за исходные сессии из шести вопросов — с 2559.0 до 2367.7 МиБ. Сравнение включает одновременно меньший контекст, лимит, температуру и другой prompt; вклад каждого изменения отдельно не измерялся.

При одинаковом оптимизированном профиле M → XL медиана изменилась с 108.53 до 273.13 с; размер GGUF — с 1221.5 до 1277.7 МиБ. Это сравнение двух установленных файлов квантования, а не универсальный вывод о всех Q4.

Итоговый профиль сохраняет temperature=0.3, max_tokens=1024, context=8192 и reasoning=auto с бюджетом 256. Для короткого демонстрационного прогона предпочитаем Q4_K_M: в выбранных трёх вопросах нет таймаута или обрезки, ниже медиана HTTP-времени и меньше GGUF. Это выбор по полученным измерениям, без обещания повышения точности. Оба квантования остаются доступными; оптимизированный профиль предназначен для коротких ответов. Улучшение фактической точности не гарантируется. Один seed, небольшой набор, фиксированный порядок, фоновая нагрузка ОС и нагрев ограничивают переносимость результатов. Для более устойчивой оценки повторите с несколькими seed и изменённым порядком вариантов.

## Воспроизведение

```bash
.venv/bin/python scripts/benchmark_local_llm.py --seeds 42 --output docs/local-llm-day29-results.json
# Расширенный прогон:
.venv/bin/python scripts/benchmark_local_llm.py --seeds 42 43 44 --output /private/tmp/day29-expanded.json
```

Сценарий сохраняет quality=null: смысловую оценку нужно заполнить после чтения всех ответов. Промежуточный JSON после прерывания не является завершённым сравнением. Benchmark не меняет пользовательские файлы памяти; временные состояния удаляются, собственные процессы останавливаются в finally.
