## Context

Ссылка на мотивацию: `proposal.md` (Why). Сейчас логика «что отправить в LLM» живёт в
`TabletopAITUI._handle_question` (`ui/tui_app.py`): сборка system/user-промптов, выбор
`max_tokens`/temperature/model, вызов `client.ask_with_usage`, проверка JSON. Оркестрация
`/logictask` дублирует в `_run_strategy` цикл «спиннер → запрос → обработка APIError»
(локальная `_call`). История существует в двух несвязанных видах: `HistoryManager`
(экран + `history.json`) и ничего — модель контекста не видит, что зафиксировано в спеке
`api-integration` как «История не отправляется».

Ограничения, которые нельзя сломать:
- e2e-слой (`StubAPI`) записывает каждый запрос: ассерты про system-сообщение по формату,
  лимиты слов/списка в user-промпте, `max_tokens`, температуру, отсутствие `stop`, повторы.
- Reasoning-модели пула тратят `reasoning_content` из бюджета выхода: `max_tokens` — потолок
  ответа, трогать его из-за роста входа не нужно.
- Юнит-тесты конструируют `TabletopAITUI(console=, history=, client=)` — сигнатура сохраняется.

## Goals / Non-Goals

Goals:
- Одна сущность агента, инкапсулирующая «вопрос → промпт → LLM → ответ» (задача дня 6).
- Многоходовой контекст сессии с ограниченной глубиной.
- Устранение дублирования оркестрации `/logictask` между UI и клиентом.

Non-Goals:
- Персистентность LLM-контекста между запусками (реплей остаётся показом).
- Инструменты/планирование/циклы агента — только пересылка контекста и фиксированные прогоны.
- Изменение параметров запроса (формат, объём, температура, модель, `stop`) — не меняются.
- Изменение поведения прогонов `/logictask` — переносится без семантических правок.

## Decisions

### D0: Конфиг и метрики агента
Конфигурация агента — один объект `AgentConfig` (сессийные `AnswerSettings` + модель сессии;
плоские свойства чтения `format`/`max_words`/`list_limit`/`temperature`, валидация остаётся
в `AnswerSettings.with_*`). Метрики последнего запроса (время, токены, стоимость) агент хранит
сам — read-only свойство `last_result` (`AnswerMeta`), обновляется каждым успешным вызовом
`ask()` и каждого запроса прогона `/logictask`; UI не дублирует их у себя.
- Альтернатива — пять разрозненных атрибутов агента и хранение метрик в UI: теряется единая
  точка конфигурации «агент как сущность», метрики размазываются.

### D1: Стек сообщений ограничен HISTORY_LIMIT (50), реплей его не засеивает
Агент хранит ходы user/assistant успешных обменов и шлёт их целиком; ходы старше 50 обменов
в запрос не попадают. Контекст — сессия-only: после рестарта стек пуст.

- Почему 50: переиспользуем существующую `config.HISTORY_LIMIT` — одинаковая ёмкость файловой
  истории и контекста; поведение предсказуемо и уже документировано. Альтернатива — безлимитный
  стек: дешевле в реализации, но стоимость входа растёт линейно и на длинных сессиях есть риск
  переполнения контекстного окна модели.
- Почему реплей не сеет стек: симметрично session-only `AnswerSettings`; иначе первый вопрос
  после рестарта унёс бы всю прошлую переписку в токенах. Альтернатива (с! seeding) отклонена.
- Оценка худшего случая: 50 × (вопрос ~60 ток + ответ до ~1400 ток) ≈ 70–75k токенов входа +
  4050 на выход — с запасом влезает в контекстные окна моделей пула, отдельная таблица окон
  (аналог `MODEL_PRICING`) не нужна.

### D2: system не хранится в стеке, пересобирается на каждый запрос
В стеке только ходы user/assistant; system собирается из активных `AnswerSettings` при каждом
`ask()`. Смена формата через `/settings` действует на следующий же вопрос; прошлые user-ходы
сохраняют свои инструкции объёма/лимита списка на момент вопроса.
- Альтернатива — хранить system первым элементом и заменять при смене настроек: то же
  наблюдаемое поведение, но лишнее состояние и риск рассинхрона. `build_system_message` уже
  `lru_cache`-нута, пересборка дешева.

### D3: APIClient переходит на messages=[...]
`_request()` шлёт массив сообщений; пара `system/user` остаётся частным случаем поверх общего
пути (совместимость с существующими вызовами/тестами). Стандартный формат Chat Completions —
агенту не нужно ничего «уплощать».
- Альтернатива — агент собирает payload сам, минуя клиента: ломает инкапсуляцию транспорта
  и дублирует знание формы запроса.

### D4: /logictask переезжает в агента, вызовы — вне стека
`solve_logictask(strategy)` в агенте делает 1/1/2/3 запроса по стратегии с параметрами прогонов
(модель сессии, без температуры, `max_tokens` от `DEFAULT_MAX_WORDS`) и yield'ит
`(label, AnswerMeta)` по мере выполнения — TUI печатает анимацию и метрики по мере прихода,
включая промежуточный промпт стратегии 3. Результаты в стек не попадают (спека `prompt-strategies`:
«Прогоны не попадают в историю» — расширяется на контекст). Дублирующая `_call` в UI исчезает.
- Альтернатива — оставить оркестрацию в UI и завести у агента только «сырой» вызов: не
  инкапсулирует логику запрос/ответ, что противоречит цели изменения.

### D5: Агент молчит, ошибки — исключением
`ask()` и `solve_logictask()` ничего не печатают; `APIError` отдаётся вызывающей стороне. Показ
ошибки, спиннер, анимация печати, история, счётчик диалогов — в TUI.
- Альтернатива — возвращать `Optional[AnswerMeta]` с заполненным `last_error`: сохраняет
  текущую форму, но смешивает домен и представление.

## Risks / Trade-offs

- [Стоимость входа растёт с каждым ходом сессии] → кап 50 обменов (D1); строка метрик честно
  показывает рост `prompt_tokens` — это ожидаемая цена контекста, а не регрессия.
- [Существующие e2e-ассерты видят ровно два сообщения в запросе] → ассерты про system/user
  остаются валидными для первого вопроса; для последующих добавляются новые ассерты (стек,
  кап, /clear, logictask-нейтральность). Повтор(e2e) после переноса обязателен.
- [Ответ модели может измениться из-за контекста (нестабильные снапшоты?)] → снапшоты снимают
  экран, а не ответ модели (stub отдаёт фиксированные ответы) — риска нет; проверяется прогоном.
- [Многоходовость усиливает промпт-инъекции из прошлых ходов] → инструкции формата и анти-
  переопределения живут в system (пересобирается каждый раз, D2); тематический контроль — на
  стороне модели, изменение политики не предполагается.

## Migration Plan

1. `core/tabletop_agent.py` + messages-режим клиента + юнит-тесты агента.
2. Переключение `TabletopAITUI` на агента (обычный вопрос, затем `/logictask`), удаление
   дублей из UI.
3. Обновление e2e-ассертов (контекст, кап, /clear) и прогон полного `pytest`.
4. Откат — revert ветки; новые ассерты откатываются вместе с кодом, старые остаются валидными.
