## Why

Задача дня 6 челленджа («Первый агент») требует, чтобы агент был отдельной сущностью, а логика
запроса и ответа — инкапсулирована в нём. Сейчас эта логика размазана по вью-классу
`TabletopAITUI`: сборку промптов, выбор параметров запроса и валидацию ответа выполняет класс
терминала (`ui/tui_app.py`), оркестрация прогонов `/logictask` дублирует в нём же цикл
«спиннер → запрос → обработка ошибки». Кроме того, каждый вопрос уходит в модель без контекста —
модель не видит предыдущих обменов сессии.

## What Changes

- Новый модуль `core/tabletop_agent.py` с классом `TabletopAgent` — единственным местом, где
  решается, что и как отправляется в LLM:
  - агент владеет стеком сообщений сессии (`system` + ходы `user`/`assistant`) и пересылает его
    в API целиком: запросы становятся многоходовыми (модель видит контекст сессии);
  - стек ограничен последними `HISTORY_LIMIT` (50) обменами — те же 50, что у файловой истории;
    стоимость запроса перестаёт расти после этого порога;
  - `system`-сообщение в стеке не хранится: агент пересобирает его из актуальных
    `AnswerSettings` при каждом запросе (смена формата в `/settings` действует сразу);
  - `ask(question) -> AnswerMeta` — обычный вопрос; ошибки API отдаёт исключением, показ решает UI;
  - `solve_logictask(strategy) -> iterator[(label, AnswerMeta)]` — прогоны `/logictask` перенесены
    из `ui/tui_app.py` в агента; вызовы прогонов идут вне стека (в контекст сессии не попадают);
  - `reset()` — сброс стека (команда `/clear`).
- `APIClient` принимает список сообщений (`messages=[...]`) вместо пары `system/user`; прежняя
  пара остаётся как частный случай поверх общего пути.
- `TabletopAITUI` становится тонким view: input-цикл, команды, рендеринг, спиннер/анимация печати,
  `HistoryManager`; сборка промптов и прямые вызовы клиента из него уходят.
- Реплей `history.json` при старте остаётся только показом: он не засеивает стек агента — контекст
  LLM живёт в рамках сессии (симметрично session-only `AnswerSettings`).
- Наблюдаемое поведение вопроса меняется: второй и последующие вопросы в сессии отправляются
  вместе с предыдущими ходами; первое поведение сессии и все параметры (формат, объём, лимит
  списка, температура, модель, отсутствие `stop`) не меняются.

## Capabilities

### New Capabilities

- `agent`: сущность агента — владение стеком сообщений сессии (кап `HISTORY_LIMIT`),
  пересборка `system` на каждый запрос, метод `ask()` для вопросов, `solve_logictask()` для
  прогонов вне стека, `reset()` для сброса контекста.

### Modified Capabilities

- `question-answering`: запрос несёт контекст сессии (предыдущие ходы) вместо одиночного
  user-сообщения; `/clear` сбрасывает контекст вместе с историей.
- `api-integration`: форма запроса к модели — массив `messages`, а не пара `system/user`.
- `history-persistence`: реплей истории при старте не влияет на LLM-контекст (история —
  показ и файл, не контекст).
- `prompt-strategies`: прогоны не попадают в стек контекста агента (само поведение прогонов —
  стратегии, параметры, счётчики — не меняется).

## Impact

- Код: новый `core/tabletop_agent.py`; `core/api_client.py` (запрос массивом сообщений);
  `ui/tui_app.py` (делегирование агенту, удаление `_call`/сборки промптов).
- Тесты: юнит-тесты агента (стек, кап, пересборка system, logictask вне стека, reset);
  e2e-ассерты, что второй запрос содержит первый ход и его ответ, `/clear` и `/logictask`
  стек не дополняют; существующие ассерты промптов и параметров остаются зелёными.
- Документация: `README.md`, `CLAUDE.md` (архитектура: агент как отдельный слой).
