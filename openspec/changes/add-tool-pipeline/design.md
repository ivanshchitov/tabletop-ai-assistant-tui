## Context

День 17 дал автоматический вызов одного инструмента на вопрос (`_choose_and_call_tool`: вспомогательный запрос выбора → `call_mcp_tool` → системное сообщение с результатом). День 18 нарастил собственный сервер `dnd-rules` планировщиком. День 19 требует композицию: search → summarize → saveToFile, автоматически и с корректной передачей данных. Пользователь поставил условие: инструменты — в существующем собственном MCP-сервере, новых серверов нет.

## Goals / Non-Goals

**Goals:**
- три инструмента одного сервера, пригодных к сцеплению: поиск с подробностями, сводка, сохранение;
- агент выполняет цепочку сам, по одному запросу выбора;
- передача данных между шагами дословная и проверяемая тестом и глазами (объёмы в журнале).

**Non-Goals:**
- адаптивная цепочка (перевыбор после каждого шага по результату);
- ручная команда цепочки (`/tool call` остаётся одиночным вызовом);
- сводка силами LLM на стороне сервера (MCP sampling).

## Decisions

**1. Цепочка планируется целиком одним запросом выбора.** Ответ `{"steps": [{"tool", "arguments"}, …]}`; прежний `{"tool": …}` — цепочка из одного шага. Альтернатива — перевыбор после каждого шага: гибче (может обойти пустой поиск), но каждый выбор стоит ~3200 prompt-токенов каталога и 800–1600 reasoning-токенов у моделей пула, т. е. цепочка из трёх шагов — четыре лишних запроса и минута-полторы ожидания. Одна цепочка — один запрос; сбой шага и так останавливает цепочку.

**2. Данные передаются ссылкой `$N`, подставляет агент.** Строковый аргумент, целиком равный `$N`, заменяется полным текстом результата шага N. Модель данные не перепечатывает: это и дешевле (текст поиска не проходит через вывод модели), и единственный способ гарантировать «корректность передачи» — подстановка детерминированная, её проверяет юнит-тест, а журнал печатает объёмы источника и приёмника. Подстановка только при точном равенстве: встраивание в строку (`"см. $1"`) породило бы вопросы экранирования и случайных совпадений.

**3. Ошибка — протокольный признак `isError`, сервер ставит его для всех своих инструментов.** До сих пор отказ возвращался обычным текстом, и клиент не мог отличить «Неверные аргументы: …» от данных: в цепочке такой текст ушёл бы в сводку как вход. `call_result` уже возвращает признак успеха (его завёл планировщик) — сервер кладёт его в `CallToolResult.isError`, а `MCPClient` уже превращает его в `MCPError`. Побочный эффект для одиночного вызова дня 17: отказ теперь приходит как `error` снимка (строка «Инструмент не вызван: …» с текстом причины), а не как данные для ответа модели — поведение честнее.

**4. Сводка детерминированная.** У сервера нет доступа к модели; сводка по полям записи (название, уровень/школа для заклинаний, тип/класс опасности для монстров — берутся известные поля, какие есть, плюс первое предложение `desc`) воспроизводима и проверяема. Вход — текст; сервер ищет в нём JSON (массив записей или объект с `results`), иначе строки-пункты `- index: name`. Подробный поиск кладёт JSON после строки-заголовка.

**5. Новые инструменты — модуль `mcp_server/pipeline_tools.py`, диспетчеризация в `dnd_server.py` по множеству имён,** как у планировщика. В `TOOLS` планировщика они не входят: ставить сохранение файла по расписанию без входных данных бессмысленно. Имена — `dnd_summarize` и `save_to_file`: `summarize` как подстрока встречается в `core/` (суммаризатор), и тест «ни одного имени инструмента в `core`/`ui`» упал бы — тот же приём, что `schedule_summary` в день 18.

**6. Каталог выгрузок — `TABLETOP_EXPORTS_DIR`, по умолчанию `exports/`.** Пишет серверный процесс, поэтому переменная — в `env_keys` записи `dnd-rules` и в `harness.AppSession` (грабли агентского цикла: без обоих прогон писал бы в реальный каталог). Имя файла: только `[\w.-]`, без `..`, расширение `.md` добавляется; занятое имя получает `-2`, `-3`…

**7. Состояние агента.** `last_tool` сохраняется (последний шаг — для совместимости с кодом и тестами дня 17), добавляется `last_tool_chain: Tuple[MCPToolResult, …]` и в `MCPToolResult` — `step`, `total`, `sources: Dict[str, int]` (аргумент → номер шага-источника) и `skipped` у последнего снимка для шагов сверх потолка. Системное сообщение результата строится по всей цепочке; аргумент-ссылка рендерится как `← шаг N`.

## Risks / Trade-offs

- Модель может не догадаться о ссылках → промпт выбора получает правило и пример цепочки; живой прогон в демо проверяет.
- Каталог инструментов растёт на два описания (~300 токенов в каждом запросе выбора) → принято, это цена функции.
- Результаты всех шагов в запросе увеличивают prompt → подробный поиск ограничен лимитом (≤10 записей) и основными полями, не полной записью.
- Смена поведения одиночного вызова при отказе (решение 3) → существующие тесты, опиравшиеся на текст ошибки как данные, обновляются с комментарием.
