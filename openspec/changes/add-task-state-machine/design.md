# Design: конечный автомат задачи и конвейер её ведения

## Почему так

Агент уже владеет диалогом, памятью и профилем, но состояние задачи — единственное, что он не держит: без него
каждый ход начинается заново. Формализуем задачу как **конечный автомат в коде** (Planning → Execution →
Validation → Done), а не как договорённость с моделью: переходы, круги правок и попытки проверки задаёт таблица
переходов, поэтому поведение детерминировано, тестируется без сети и не может «поехать» от нестабильного ответа
модели. Модель делает содержательную часть — план, разделы артефакта, ревью, — но ни одного перехода не
выбирает.

## Разделение слоёв

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `core/task_state.py` | Состояние задачи: очередь, этапы, шаги, ожидаемое действие, план, артефакт, замечания, пауза. Чистые переходы и терпимое хранилище `task.json`. Сообщение состояния для запроса. | только `json`, `config` |
| `core/task_pipeline.py` | Шаговый исполнитель: одна операция конвейера за вызов (запрос планирования, выполнение подзадачи, проверка, итог), разбор ответов, запись состояния | `task_state`, клиент через инъекцию |
| `core/tabletop_agent.py` | Владение состоянием и конвейером; запросы конвейера уходят модели тем же клиентом; фазы; учёт расхода; снимок `TaskReport` для интерфейса | `task_state`, `task_pipeline` |
| `ui/tui_app.py` | Команда `/task`, цикл прогона, живая панель, клавиша паузы, строка статус-бара | `core.task_*`, `keyboard` |

Терминальный слой не знает ни одного правила автомата: он печатает снимок и рисует панель. Агент не печатает
ничего. Конвейер не знает ни про `rich`, ни про HTTP: запрос к модели он получает инъекцией
(`ask(messages, max_words, phase) -> AnswerMeta`), поэтому проверяется юнит-тестом с фальшивым запросом.

## Состояние

`TaskState` — снимок всего, что переживает перезапуск:

- `tasks: Tuple[TaskItem, ...]` — очередь по порядку постановки;
- `paused: bool` — признак паузы;
- `awaiting_edits: bool` — этап Planning ждёт ответа пользователя о правках (важно для паузы посреди Planning).

`TaskItem`: цель (обрезанная до `TASK_GOAL_MAX_CHARS`), статус (`ожидает`, `в работе`, `решена`, `не удалось`),
план (`Tuple[str, ...]`), разделы артефакта (`Tuple[TaskSection, ...]`: подзадача, текст, признак невыполненной),
замечания проверки, номер круга планирования, номер попытки проверки, причина сбоя.

Активная задача — первая незавершённая; отдельного указателя нет, поэтому очередь не может «застрять» на
сбитом индексе.

**Текущий шаг** и **ожидаемое действие** — производные свойства (не хранятся отдельно, чтобы не рассинхрониться
с этапом):

| Этап | Текущий шаг | Ожидаемое действие |
|---|---|---|
| Planning | «круг N, подзадач M» или «жду правок», если `awaiting_edits` | «построить план» / «дождаться правок пользователя» |
| Execution | «k/M: формулировка подзадачи» | «выполнить подзадачу» |
| Validation | «попытка k/2», при исправлении — «правки по замечаниям» | «сверить артефакт с планом» |
| Done | «итог отправлен» | «взять следующую задачу из очереди» |

## Переходы

```
Planning --(правки есть, круг < MAX_PLAN_ROUNDS)--> Planning (круг+1)
Planning --(правок нет / круг исчерпан)----------> Execution
Execution --(остались подзадачи)----------------> Execution (следующая)
Execution --(все подзадачи выполнены)-----------> Validation
Validation --(замечаний нет)--------------------> Done
Validation --(замечания, попытка < MAX_VALIDATION_ATTEMPTS)--> Execution (исправление)
Validation --(замечания, попытки исчерпаны)------> Done
Done --(очередь не пуста)-----------------------> Planning (следующая задача)
Done --(очередь пуста)--------------------------> остановка прогона
```

Переход выполняется только вместе с записью состояния на диск — порядок «сначала записать, потом следующий
запрос» и есть причина, по которой пауза и прерывание ничего не теряют.

## Хранение

`TaskStore` пишет `task.json` (`TABLETOP_TASK_FILE`) конвертом
`{"version": 1, "paused": bool, "awaiting_edits": bool, "tasks": [...]}`. Чтение терпимое, как у остальных
хранилищ проекта: нет файла, битый JSON, чужая форма — пустая очередь без ошибки; незаполненные поля задачи
дочитываются значениями по умолчанию. Запись атомарная (во временный файл рядом и `os.replace`) — состояние
переживает прерывание в момент записи. Ошибка записи не роняет прогон (как у `profile.json`), но сообщается
строкой.

## Запросы конвейера

Три вида, каждый — своё системное сообщение из ассета плюс данные задачи:

| Операция | Ассет | Пользовательское сообщение | Ожидаемый ответ |
|---|---|---|---|
| План | `assets/task_plan_prompt.md` | цель, прежний план, правки пользователя | JSON `{"items": [...]}`, разбирается клиентской стороной |
| Выполнение | `assets/task_execute_prompt.md` | цель, план, текущая подзадача, уже написанные разделы | markdown-раздел артефакта |
| Проверка | `assets/task_validate_prompt.md` | цель, план, артефакт | JSON `{"ok": bool, "issues": [...]}` |

Параметры: модель сессии, без температуры сессии (клиентский дефолт — как у суммаризатора и извлекателя), прижатый
`max_tokens` от `config.TASK_MAX_WORDS`. `response_format` не используется: у reasoning-моделей он ненадёжен, а
разбор всё равно клиентский — берём первый JSON-объект из ответа и считаем неразобранный ответ сбоем операции
(как у извлекателя фактов). Запросы конвейера идут мимо `_shrink_to_ceiling` и порога сжатия: их состав задан
задачей, а не диалогом.

`assets/task_prompt.md` — инструкция к системному сообщению состояния, которое уходит в **диалоговые** запросы
(когда очередь непуста): вести пользователя по текущему шагу, не перескакивать этапы и не спрашивать заново то,
что уже пройдено. Пустая очередь сообщения не добавляет — форма запроса без задачи не меняется.

## Прогон, пауза и видимость

Цикл живёт в `ui/tui_app.py`: перед каждой операцией опрашивается клавиатура
(`keyboard.read_key_nowait()` — неблокирующее чтение, потому что панель обновляется, а ввод не блокируется),
затем выполняется один шаг конвейера, состояние перерисовывается в панели. Пауза (`p` или `\x03`) прекращает
цикл: панель закрывается, печатается строка с этапом и шагом, приглашение возвращается. Во время прогона
терминал в cbreak-режиме (как на экранах `/settings`), а он сохраняет ISIG, поэтому Ctrl+C приходит
сигналом и переводится в паузу, а не в выход,
а не как выход: пауза безопаснее, работа не теряется.

Панель — временный `rich.Live`: создаётся первым шагом прогона, закрывается в `finally`, ничего не пишет в
скроллбэк и в файлы. В журнал попадают только строки, которые печатает приложение: метрики `⏱` по каждому
запросу (существующая конвенция), вопрос о правках, строка паузы, summary этапа Done и строка окончания прогона.

## Разбор отказов

| Отказ | Поведение |
|---|---|
| Запрос планирования (ошибка API или неразобранный ответ) | повтор запроса клиентом; исчерпали — задача `не удалось` с причиной, очередь идёт дальше |
| Запрос выполнения подзадачи | раздел помечается невыполненным с причиной; остальные подзадачи выполняются; проверка это находит |
| Ревью проверки | детерминированные проверки дают вердикт; итог сообщает, что модельная проверка недоступна |
| Запись состояния | прогон продолжается, строка об ошибке записи в журнале |
| Пауза во время запроса | запрос доводится до конца, пауза срабатывает на границе операции |

## Тестирование

- Юнит: переходы автомата (каждая ветка схемы выше), пауза/продолжение на каждом из четырёх этапов, терпимое
  чтение битого файла, производные поля шага и ожидаемого действия.
- Юнит: конвейер с фальшивым запросом (план, разделы, вердикт, каждая ветка отказов), разбор JSON плана и
  вердикта, прижатый `max_tokens`.
- Юнит: команда `/task` и рендер панели на фальшивой консоли; `read_key_nowait` — в реальном псевдотерминале.
- E2e: полный прогон двух задач без паузы (stub видит порядок и состав запросов: план → выполнение → проверка,
  повторный план после правок), пауза клавишей и продолжение с того же шага, перезапуск приложения продолжает
  с сохранённого состояния, `/clear` очередь не трогает, `task.json` репозитория не тронут.
- Ждать в e2e — только отрисованный маркер (текст панели, строка итога): живая панель перерисовывается, «тишины»
  вывода не бывает.

## Рассмотренные альтернативы

- **Переходы отдаёт модель** (просим её сообщать «этап закрыт»): недетерминизм, невозможность доказать паузу и
  прыжки через этапы — отвергнуто на этапе плана.
- **Конвейер в терминальном слое**: решение о том, что уходит в LLM, оказалось бы в UI — против архитектурного
  правила проекта.
- **Артефакт отдельным файлом на задачу**: ещё один файл состояния, ещё один переключатель и изоляция в тестах
  ради того же результата; история проекта держит текст ответов в конверте, поэтому артефакт живёт в `task.json`.
- **Отдельная панель-экран для задач** (как `/settings`): состояние меняет агент, а не клавиши, — редьюсер тут не
  нужен, достаточно живой панели и отчёта.
