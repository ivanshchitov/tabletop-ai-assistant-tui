# Design: инварианты агента

## Context
См. `proposal.md` — Why. Что есть сейчас и что задаёт рамки:
- `core/memory_layers.py` — образец **таблицы правил в коде** (`RULES`): детерминированные правила, тест на
  каждое, отчёт интерфейса печатает их, чтобы пользователь видел, почему что-то произошло.
- `core/user_profile.py` — образец слоя, который уходит модели отдельным системным сообщением с инструкцией из
  ассета (`profile_message()` + `assets/profile_prompt.md`) и отдаётся интерфейсу снимком (`ProfileReport`).
- `core/tabletop_agent.py` — единственное место, решающее, что уходит модели: `_build_messages` (system →
  профиль → задача → память → память стратегии → ходы → новый user-ход), `ask()` (маршрут памяти, подготовка
  контекста, запрос, `_remember`, `history.add`), `_ask_task` (запросы конвейера — модель сессии, без
  температуры, прижатый потолок, расход в накопителе). Снимки `context_report()`/`memory_report()`/
  `profile_report()` — граница изоляции интерфейса.
- `core/task_pipeline.py` — собирает свои запросы сам: `[system этапа, user]`, и отдаёт их в инъецированный
  `ask(messages, max_words, phase)`.
- `ui/tui_app.py` — печатает ответ, строку `⏱`, предупреждения об обрезке и о невалидном JSON (по
  `agent.last_result`), журнальные строки маршрутизации и фактов — все экранные, никогда не в `history.json`.
- `question-answering`: тематический контроль — только на стороне модели; фиксированная фраза отказа на
  внетематический вопрос — контракт промпта, известный тестам.
- Ограничения проекта: `core/` без `rich`, снимки вместо чтения внутренностей, OpenSpec + TDD, новых файлов
  состояния — нет (пользователь: инварианты фиксированы, без команд управления).

## Goals / Non-Goals

**Goals:**
- Инварианты как отдельная сущность агента: не диалог, не память, не профиль; уходят в каждый запрос и в
  конвейер.
- Двойная защита — инструкция модели и проверка кодом, повторный запрос с нарушениями, отклонение ответа.
- Отказ объяснён: и отказ модели, и отказ приложения называют инвариант и причину.
- Всё тестируемо без терминала и без модели: таблица, проверка, повтор — чистые функции и фейковый клиент.

**Non-Goals:**
- Команды добавления/удаления инвариантов, файл инвариантов, переключатель среды (решение пользователя).
- Проверка разделов артефакта конвейера кодом: по правилу дня 13 готовый раздел не переделывается, поэтому
  замечание было бы только отчётным; конвейер получает инварианты промптом.
- Семантическая проверка правил без слов («не дольше двух часов»): регулярки по числам ненадёжны; такие
  инварианты держит промпт, и отчёт честно это показывает.
- Классификация вопроса до запроса (клиентская фильтрация): противоречит `question-answering` — просьба
  всегда доходит до модели, отказ формирует модель, код лишь не пропускает нарушивший ответ.

## Decisions

**D1 — таблица инвариантов в коде (`core/invariants.INVARIANTS`), не файл.** Пользователь просил фиксированный
набор; кодовая таблица — тот же приём, что `memory_layers.RULES`: по тесту на инвариант, ни файла состояния,
ни `TABLETOP_*`-переключателя, ни pass-through в harness. Альтернатива — `assets/invariants.md` по README
недели — разделила бы правило (текст) и запрещённые слова (структура) по двум местам, либо потребовала бы
парсер; в `assets/` живут только инструкции модели.
`Invariant(number, rule, forbidden: tuple[str, ...])` — замороженный датакласс; `forbidden` пуст у правил,
проверяемых только моделью.

**D2 — двойная защита: сообщение + проверка.** `assets/invariants_prompt.md` — инструкция (сверить просьбу с
каждым инвариантом до ответа; конфликт → отказ с фиксированным началом «Не могу предложить», номер и правило,
объяснение; альтернатива только в рамках; инварианты выше профиля, памяти и свежей реплики — единственное
исключение из правила «свежая реплика важнее»). `invariants_message()` = перечень «N. правило» + инструкция;
запрещённые слова модели **не** уходят: правило «без приложений» и так ясно, а список слов провоцировал бы
модель обходить проверку синонимами вместо соблюдения правила.

**D3 — распознавание отказа модели по фиксированному началу.** `check_answer(text)` пропускает ответ, в первых
`REFUSAL_WINDOW` (200) символах которого есть `REFUSAL_PREFIX` («Не могу предложить»): отказ *называет*
запрещённое («игры с приложением») и решения не предлагает. Окно, а не «начинается с»: в JSON-формате отказ
лежит внутри `{"error": "..."}` в блоке кода, в compact — после маркера формата. Слабость: решение, спрятанное
после фразы отказа, проверку обойдёт — это ложь модели, которую подстрочная проверка не ловит в принципе
(см. Risks); приём тот же, что фиксированная фраза внетематического отказа в `question-answering`.

**D4 — проверка по вхождению, регистронезависимо.** `casefold()` обеих сторон, вхождение оборота; слова
таблицы — основы (`монопол`, `приложени`), чтобы ловить падежи без морфологии. Нарушение — `Violation(number,
rule, term)`, `term` — оборот из таблицы, не фрагмент ответа (стабильный текст для журнала и тестов).

**D5 — повтор как продолжение диалога, не новый запрос с нуля.** Повторный запрос = те же сообщения + ход
`assistant` с нарушившим ответом + ход `user` «Ответ нарушает инварианты: … Перепиши ответ без нарушений или
откажи…». Это буквально «повторяем запрос с новыми вводными» из README недели, и модель видит, *что* именно
не так. `config.INVARIANT_RETRIES = 1`: второй повтор — та же вероятность нарушения за ещё одну цену. Расход
обоих запросов — в накопителе; `last_result` — последний запрос (строка `⏱` показывает его; сумма — в
`/usage`).

**D6 — отклонение: отказ приложения вместо ответа.** `refusal_text(violations)` — «Не могу предложить: ответ
нарушает инвариант N «правило» (в ответе: «слово»)». В стек и в `history.json` ложится этот текст: история
хранит то, что видел пользователь, а не отклонённый ответ; иначе следующий вопрос нёс бы модели нарушивший
ход как образец. Отказ приложения — не ответ модели, поэтому при JSON-формате предупреждение о невалидном
JSON не печатается (`last_invariants.rejected`); формат ответа задаёт модель, а не приложение.

**D7 — журнал только о нарушениях, статус-бар без изменений** (решение пользователя). `InvariantsCheck`
(`violations`, `retried`, `rejected`) в `agent.last_invariants`; `ui` печатает «⛔ Инвариант N нарушен
(«слово») — повторный запрос» и «⛔ Ответ отклонён: инвариант N …». Соблюдённые — молчание: журнал не
засоряется строкой на каждый ответ (та же логика, что отсутствие `⏱` в прогоне задачи).

**D8 — конвейер: сообщение вставляет агент, не конвейер.** `_ask_task` вставляет `invariants_message()`
вторым сообщением (после system этапа): конвейер не знает об инвариантах, как не знает о модели и потолке —
«что уходит модели, решает агент». Проверка разделов кодом — Non-Goal.

**D9 — место в стеке: сразу после профиля, выше задачи и памяти.** Инварианты — жёсткие рамки; чем выше, тем
меньше шанс, что более поздняя инструкция (профиль, свежая реплика) их перекроет. Сообщение есть **всегда**
(таблица непуста по построению), поэтому форма запроса меняется во всех тестах, где проверяется состав
сообщений — это осознанная смена контракта, e2e/unit-ожидания обновляются с комментарием.

## Risks / Trade-offs
- [Решение, спрятанное после фразы отказа] → подстрочная проверка не ловит; промпт прямо запрещает
  альтернативы вне инвариантов; честно описано в `CLAUDE.md`.
- [Ложное срабатывание основы слова («соло» в «Соломон», «покер» в «покерные фишки»)] → повторный запрос
  даёт модели переформулировать; отклонение — только после второго нарушения; основы выбраны узкими и по
  тесту на каждую (положительный и отрицательный).
- [Отказ модели без фиксированного начала («Извините, инвариант 3 запрещает Монополию»)] → слово найдено →
  повторный запрос с перечнем → модель отвечает отказом по инструкции; цена — один запрос. Это и есть двойная
  защита.
- [Ещё одно системное сообщение в каждом запросе] → ~150 токенов; формат запроса без инвариантов больше не
  существует, что меняет ожидания тестов состава сообщений — обновляются осознанно.
- [Модель нарушает инвариант без слов] → ловит только промпт; в отчёте такие инварианты помечены явно.
