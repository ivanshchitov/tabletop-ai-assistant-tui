## Context

См. `proposal.md` для цели и критериев дня 30. Существующий TUI поддерживает локальные идентификаторы и `TABLETOP_LOCAL_API_URL`, объединяет system-сообщения Qwen и не передаёт облачный ключ локальной модели. `TABLETOP_LLAMA_AUTOSTART=0` уже отключает управление сервером клиентом. Отдельный сервис дополняет эти механизмы.

## Goals / Non-Goals

**Goals:** один домашний сервер, одна локальная модель, текстовый чат через совместимый HTTP API, проверяемые лимиты и отдельный процесс с корректным завершением.

**Non-Goals:** браузерный интерфейс, потоковые ответы, аккаунты, база диалогов на сервере, несколько моделей, публикация в Интернете и нагрузочное исследование десятков клиентов.

## Decisions

### Процессы и запуск

`tabletop-llm-service.py` запускает отдельный одиночный llama-server на `127.0.0.1:10099`, ожидает его готовности, затем обслуживает шлюз на `127.0.0.1:8080` по умолчанию. Сетевой адрес привязки задаётся аргументом `--host`; документация использует `<SERVER_LAN_IP>` и `<CLIENT_LAN_IP>`. Backend использует уже загруженную Qwen3.5-2B Q4_K_M через `--hf-repo`, alias `tabletop-qwen-2b-q4-k-m-optimized`, контекст 8192, один слот, температуру 0.3, reasoning=auto, thinking budget=256 и `--no-context-shift`. Допускается явный путь к GGUF для машины без кэша. Клиент не выбирает другие модели через шлюз.

Запущенный дочерний сервер принадлежит только сервису; занятый backend-порт даёт ошибку, существующий процесс не присваивается и не останавливается. SIGINT/SIGTERM, ошибка запуска и выход шлюза завершают только созданную группу процессов. Отдельный конфигурационный INI не нужен: действующий router TUI не меняется. Для Linux предоставляется пример systemd-unit с placeholders, окружением из отдельного файла и Restart=on-failure; на Mac сервис запускается самостоятельной командой.

### HTTP-контракт и авторизация

Используем стандартную библиотеку Python (`http.server`) и существующий `requests`; новых зависимостей продукта не требуется. Публичные маршруты ограничены:

- `GET /health`: только готовность, 200 или 503; без текстов, путей и секретов.
- `GET /v1/models`: единственная модель, требуется ключ.
- `POST /v1/chat/completions`: `model`, `messages`, `max_tokens`, `temperature`, опциональные `seed`, `cache_prompt`, `stream=false`; требуется ключ. Отсутствующий model выбирает сервисную модель.

Ключ `TABLETOP_SERVICE_API_KEY` обязателен при старте, проверяется как `Authorization: Bearer ...` постоянным по времени сравнением. Клиент использует независимый `TABLETOP_LOCAL_API_KEY` только для локальной модели; без него существующий локальный режим продолжает работать без Authorization. Ключи не включаются в аргументы процессов, ошибки или журнал. Неизвестные маршруты — 404; неподдерживаемые роли, поля, потоковый режим, неверные числовые значения и чужая модель — 400. Текстовые роли: system/user/assistant; контент — строка. При нескольких system-блоках они объединяются в начале с сохранением порядка, как в TUI.

Ответы и `usage` возвращаются в формате chat completions. Возвращённое Qwen поле `reasoning_content` допускается у assistant при передаче истории, но отбрасывается перед формированием следующего prompt. Ошибки имеют JSON-объект `error` с `message`, `type`, `code`; traceback и сырой ответ backend клиенту не раскрываются. Таймаут backend — 504, недоступность/неверный ответ — 502. Минимальный журнал содержит статус, длительность и идентификатор запроса, без заголовков и содержимого диалога.

### Ограничения

- Тело JSON не более 128 КиБ, превышение — 413; время чтения ограничено. Неверная длина и отсутствие поддерживаемой длины тела дают явный отказ.
- Ответ от 1 до 1024 токенов, по умолчанию 1024. Больший `max_tokens` отклоняется, не исправляется молча.
- Не более 10 авторизованных корректно оформленных запросов генерации в скользящие 60 секунд на ключ. Неверный контекст тоже расходует разрешённый запрос, поскольку его проверка нагружает backend. 429 содержит `Retry-After`. Проверки `/health` и `/v1/models` не расходуют лимит генерации.
- Одно исполнение и не более одного ожидающего запроса; переполнение очереди — 503 с `Retry-After`. Доступ к счётчикам синхронизирован; ограничено и число одновременных HTTP-обработчиков, чтобы очередь не создавала неограниченные потоки.
- Внутри исполнения gateway получает готовый prompt через `/apply-template` и его токены через `/tokenize` с обработкой специальных токенов. Число токенов prompt плюс запрошенный бюджет ответа и небольшой консервативный запас специальных токенов должно укладываться в 8192. Переполнение — 400 `context_length_exceeded`, без запуска генерации. Параметры шаблона при подсчёте и генерации одинаковы; backend также отключает context shift.

Точные границы и освобождение очереди после любого исключения проверяются тестами. Прямое открытие llama-server проще, но не обеспечивает выбранный лимит частоты и ограниченную очередь. Обратный прокси добавил бы зависимость ради небольшой локальной задачи; собственный минимальный шлюз подходит согласованному объёму.

### Проверка и демо

Проверки политики — с управляемыми часами и подставным backend. HTTP-тест — реальный gateway против локальной заглушки, включая конкурентные запросы, чат и поведение клиента. После реализации — реальная модель: ровно три последовательных вопроса (стоимость дороги CATAN, подготовка CATAN, условие победы CATAN), каждый с HTTP 200, непустым ответом и временем; это проверка стабильности, а не точности всего корпуса правил. Два хода TUI отдельно проверяют чат.

Сетевой запрос выполняется на ALT Linux через SSH-сеанс на экране Mac. Адрес, логин и любые локальные параметры подключения живут только в `videos/tmp/`, который исключён из Git. Пароль не хранится даже в скрипте: управляющий процесс принимает его скрытым вводом и передаёт SSH в момент выключенного эха. Ключ HTTP также вводится скрыто и не показывается в командах/журнале. Для записи автоматизируются ответы и ожидание отрисованных маркеров; готовность окна и захват всего экрана подтверждаются отдельно.

Проверка rate limit использует быстрые отказы контекста, чтобы не создавать десять дополнительных генераций: они входят в окно частоты, следующий запрос даёт 429. После истечения окна короткий запрос снова проходит. Ни эти проверки, ни два хода чата не включаются в согласованную серию стабильности из трёх вопросов.

## Risks / Trade-offs

- HTTP внутри доверенной домашней сети не шифрует трафик → инструкция ограничивает сетевой доступ; для недоверенной сети используется VPN или TLS перед шлюзом. Автоматически открывать порты роутера не требуется.
- Небольшая модель и одно исполнение ограничивают производительность → один ожидающий запрос, явный отказ перегрузки, фиксированное окно и бюджет ответа.
- API шаблона llama.cpp меняется → закрепляем проверенный build в инструкции и проверяем реальный prompt/tokenize до демо; ошибки preflight не пропускают запрос в генерацию.
- Разные настройки шаблона могут изменить число токенов → gateway принимает небольшой фиксированный набор полей и использует одни настройки для обеих стадий, консервативный запас и отключённый context shift.
- Отдельный сервис и стандартный TUI могут одновременно загрузить модель → при подключении к сервису документация явно задаёт `TABLETOP_LLAMA_AUTOSTART=0`.

## Migration Plan

Текущий локальный и облачный режимы сохраняются. Для включения сервиса запускается отдельный entry point, у клиента задаются адрес, отдельный ключ и отключение автозапуска. Возврат: остановить сервис и убрать эти три переменные из окружения клиента. Постоянные файлы диалогов не меняются.
