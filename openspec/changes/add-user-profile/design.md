# Design: персонализация агента — профиль пользователя

## Context
См. `proposal.md` — Why. Что есть сейчас и что задаёт рамки:
- `core/memory_layers.py` — слои памяти и таблица правил маршрутизации реплик; `memory_message()` собирает одно
  системное сообщение памяти (инструкция из `assets/memory_prompt.md` внутри). Категория «профиль» уже есть, но
  это **выведенная** запись из реплики, а не объявленное предпочтение.
- `core/long_term_memory.py` — образец отдельного файла состояния: `LongTermMemory(path=config.MEMORY_FILE)`,
  устойчивое чтение (нет файла или битый JSON → пусто), запись сразу после изменения, ошибка записи не поднимается.
- `core/tabletop_agent.py` — владеет хранилищами (`history`, `long_term`), собирает запрос в `_build_messages`:
  system настроек → сообщение памяти → память стратегии → ходы вида → новый user-ход; отдаёт снимки
  (`memory_report`, `context_report`) и операции, интерфейс внутренности не читает.
- `ui/tui_app.py` — команды-диспетчер (`/memory` — с значимыми аргументами), отчёты печатаются из снимков;
  ввод основного приглашения — `input()` без разметки, ручной ввод ключа — `sys.stdin.readline` (readline
  перехватывает SIGINT, поэтому Ctrl+C не поднимал `KeyboardInterrupt`).
- `core/config.py` — пути файлов состояния выводятся из `BASE_DIR` и переопределяются переменными окружения;
  новый файл состояния означает переменную и pass-through в `tests/e2e/harness.AppSession`.
- Ограничения проекта: `core/` без `rich` и терминала, настройки — неизменяемые снимки, отчёты строятся из
  снимка агента, поведение меняется через OpenSpec + TDD.

## Goals / Non-Goals

**Goals:**
- Профиль как самостоятельный слой персонализации: объявленные предпочтения, а не выведенные из реплик факты.
- Настройка профиля — диалог «вопрос — ответ» из пяти вопросов, целиком тестируемый без терминала.
- Профиль участвует в каждом запросе, но не ломает действующие контракты: формат ответа, объём, лимит списка и
  потолок токенов остаются за настройками приложения.

**Non-Goals:**
- Автоматическое выведение профиля моделью из реплик или интервью, которое ведёт модель: вопросы фиксированы, а
  маршрутизация остаётся за правилами.
- Панель-редьюсер для профиля (как `/settings`): задача просит диалог, а не форму.
- Слияние долговременной памяти и профиля, синхронизация их записей.
- Аутентификация и идентификация пользователя по внешнему id: профиль выбирает сам пользователь командой.

## Decisions

**D1 — профиль отдельный слой и отдельный файл, а не записи долговременной памяти.** Категория «профиль» в
`memory.json` — это выведенное правило, её значение вычисляется из реплики и перезаписывается роутером; профиль
персонализации объявлен пользователем в диалоге, живёт фиксированными разделами и уходит в каждый запрос.
Альтернатива — писать ответы диалога в `memory.json` — отклонена: смешала бы объявленное с выведенным, а диалог
писал бы мимо роутера в слой, у которого своя модель ключей и (в перспективе) вытеснение.

**D2 — хранилище — JSON, а не md-файл.** Недельный README (`week3`) предлагает сложить персонализацию в md-файлы,
но конвенция проекта — состояние в JSON со устойчивым чтением (`history.json`, `memory.json`), а markdown у нас
служит инструкциям модели (`assets/*.md`). Альтернатива — md с разделами — отклонена: потребовала бы парсера
секций и правил «кривой файл читается как пустой», то есть того же кода, но с риском съесть текст пользователя.
Файл: `profile.json`, путь — `config.PROFILE_FILE` (переменная `TABLETOP_PROFILE_FILE`), в `.gitignore`.

**D3 — диалог настройки: чистый автомат в `core/`, ввод — в терминальном слое.** `core/user_profile.py` держит
скрипт диалога (`QUESTIONS`: имя + по вопросу на раздел) и `InterviewState` с переходами
`question` → `answer(text)` → `profile()`; `ui/tui_app.py` только печатает вопрос, читает строку и вызывает
следующий переход. Это даёт юнит-тест на порядок вопросов, пропуск, отмену и сборку профиля без псевдотерминала —
как редьюсеры панелей. Альтернативы: (а) панель-редьюсер с полями — отклонена, это форма, а не диалог;
(б) вопросы генерирует модель — отклонена: лишние запросы, недетерминизм и невозможность проверки.
Число вопросов (5) и покрытие разделов держит тест — «не более пяти» из задачи остаётся инвариантом, а не
соглашением.

**D4 — ответы читаются `sys.stdin.readline` и отмена ловится локально.** Диалог — ввод строки, значит Ctrl+C
должен отменять настройку, а не убивать приложение (как это делает `run()` для основного цикла). `readline`
перехватывает SIGINT при `input()`, поэтому берём тот же приём, что у ручного ввода ключа
(`_read_manual_key`): чтение строки напрямую из stdin и `KeyboardInterrupt` вокруг всего диалога. Приглашение
печатается без rich-разметки — как основное, иначе readline неверно считает ширину при возврате каретки.

**D5 — место профиля в запросе: сразу после system настроек.** Порядок: system (база + инструкция формата) →
**профиль** → память слоёв → память стратегии → ходы диалога → новый user-ход. Профиль отвечает на «как
отвечать» и стабилен от вопроса к вопросу, поэтому стоит рядом с инструкциями формата; память отвечает на «что
известно» и потому идёт ниже. Инструкция ассета `assets/profile_prompt.md` добавляется в само сообщение профиля
и подчиняет предпочтения настройкам приложения — иначе профиль ломал бы контракт формата (JSON), лимит слов и
лимит списка, на которые опираются e2e-проверки. Сообщение добавляется только при непустом профиле, поэтому
форма запроса без персонализации (на неё завязаны несколько тестов) не меняется.

**D6 — активный профиль один, создание — только диалогом.** `profile.json` держит `active` и словарь профилей;
`/profile use <имя>` переключает активный профиль, но на неизвестное имя не создаёт пустышку, а сообщает, что
профиля нет: единственный вход создания — диалог настройки, иначе в запрос мог бы уходить пустой профиль и
ломать проверку «профиль без разделов сообщения не даёт». Удаление активного профиля оставляет файл без
активного: запросы уходят без сообщения профиля.

**D7 — пустой ответ оставляет раздел как был.** Пять вопросов, каждый можно пропустить, и повторная настройка
под тем же именем — редактирование профиля: ответ заменяет раздел, Enter сохраняет прежний, поэтому «случайный
Enter» ничего не стирает. Для нового профиля «как был» = пусто. Пустое имя даёт свободное имя по порядку —
приём уже есть в проекте (`_next_note_key` даёт «заметка N»).

**D8 — `/clear` профиль не трогает.** Тот же принцип, что у долговременной памяти: `/clear` отвечает на «начать
диалог с чистого листа», а профиль — не диалог. В подтверждении `/clear` уже сказано, что долговременная память
сохранена; строка дополняется профилем.

**D9 — предел длины раздела обрезает ответ при записи.** `config.PROFILE_VALUE_MAX_CHARS`: профиль уходит в
каждый запрос, поэтому его объём ограничен, как длина записи памяти (`MEMORY_VALUE_MAX_CHARS`). Обрезка — в
одном месте (хранилище профиля), и в журнал диалога попадает уже обрезанное значение: пользователь видит, что
именно сохранено, а не догадывается.

## Risks / Trade-offs

- [Профиль противоречит настройкам приложения (формат JSON, лимит слов)] → инструкция профиля прямо подчиняет
  предпочтения настройкам, а e2e проверяет, что запрос при непустом профиле несёт и инструкцию формата.
- [Профиль уходит в каждый запрос и растит расход] → предел длины раздела, сообщение только при непустом
  профиле, вклад виден в оценке токенов `/context`.
- [Модель может проигнорировать предпочтение профиля] → спеку держим на уровне наблюдаемого: «сообщение профиля
  уходит в запрос»; следование профилю проверяется демонстрацией на живой модели и не обещается как гарантия.
- [Ctrl+C во время диалога раньше завершал приложение] → диалог ловит `KeyboardInterrupt` локально и отменяет
  только настройку; поведение описано в спеке и проверяется тестом.
- [Ещё один файл состояния: прогон мог бы писать в реальный `profile.json`] → переменная
  `TABLETOP_PROFILE_FILE`, pass-through в `harness.AppSession` и e2e-проверка, что файл репозитория не тронут.
- [E2E-сценарий диалога: ответ приходит раньше вопроса] → тест и демо ждут отрисованный текст вопроса, а не
  тишину вывода; ответы отправляются по одному после появления вопроса.
