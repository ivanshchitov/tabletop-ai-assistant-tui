## Context

База уже есть: `AnswerMeta` несёт per-запросные метрики (prompt/completion/total, стоимость),
агент хранит её в `last_result`, TUI печатает строку метрик после каждого ответа. Не хватает
агрегата по сессии, видимого состояния окна контекста и видимого излома «переполнение бюджета».

## Goals / Non-Goals

- Goals: накопительная статистика сессии; оценка объёма истории в токенах без API; команда
  `/usage`; итоги сессии в статус-баре; расход, сохраняемый в записях истории; видимое
  предупреждение при `finish_reason=length`; env-override лимита истории для демо переполнения.
- Non-Goals: точный токенизатор (tiktoken и т.п.) — приближение, честно помеченное как оценка;
  автоматическое сжатие истории (history compression) — только наблюдаемость; предупреждения
  об усечении в `/logictask`; бухгалтерская точность расхода за пределами удержанной истории.

## Decisions

### 1. Накопитель — в `core/usage.py`, владелец — агент

`SessionLedger` — маленький изменяемый агрегатор с `record(meta)` и снимком полей; живёт на
`TabletopAgent`, потому что агент — единое место, через которое проходят все успешные запросы
(и вопрос, и все стратегии `/logictask`). TUI только читает. `/clear` → `agent.reset()` →
`ledger.reset()`: статистика привязана к контексту, отчёт после очистки начинается с нуля — это
согласует «итоги сессии» с «текущим контекстом».

### 2. Оценка токенов истории — эвристика, не токенизатор

`estimate_tokens(text) = max(1, ceil(len(text) / ESTIMATED_CHARS_PER_TOKEN))`,
`ESTIMATED_CHARS_PER_TOKEN = 3` (кириллический текст в клонах BPE тратит заметно больше токена
на слово, чем английский; 3 символа/токен — заниженная, консервативная оценка). Точность не
гарантируется и в отчёте помечается словом «≈»; реальный расход виден в `prompt_tokens` ответа.
Альтернатива — тянуть tiktoken: зависимость, не работающая с моделями не-GPT-семейства.

### 3. `finish_reason` — новое optional-поле `AnswerMeta`

Клиент снимает `choices[0].finish_reason` (None при отсутствии). Это данные, а не поведение:
интерпретация — в TUI. Пустой `content` + `length` → «модель исчерпала бюджет max_tokens» —
известный излом reasoning-моделей (см. главный README, раздел про `MAX_MAX_WORDS`); непустой
`content` + `length` → «ответ мог быть обрезан». Предупреждение печатается над строкой метрик;
строка метрик не меняется. `content_filter`/`tool_calls` сознательно не обрабатываются — в этом
приложении не встречаются.

### 4. `TABLETOP_HISTORY_LIMIT` — по образцу существующих переключателей

`config.HISTORY_LIMIT = int(os.getenv("TABLETOP_HISTORY_LIMIT", "50"))`. Одна константа
управляет и стеком сессии агента, и файлом истории — как и сейчас (единый `HISTORY_LIMIT`).
Некорректное значение (не число) не ловится молча: пусть падает при старте, как и остальные
`int(os.getenv(...))` в конфиге.

### 5. `/usage` — печать в постоянный лог, без интерактивной панели

Отчёт нередактируемый и мгновенный — панель-редьюсер (как `/settings`) не нужна, достаточно
`console.print`. Но команда попадает в `COMMAND_OPTIONS` → автодополнение, панель `/commands` и
диспетчер обновляются сами. Отчёт: (а) последний запрос — из `agent.last_result`; (б) итоги
сессии — из `agent.session_usage`; (в) расход всей сохранённой истории — сумма метрик по
записям файла истории; (г) окно контекста — «N/M обменов» + «≈ K токенов» из оценки стека.
До первого вопроса в сессии блок (а) печатает «пока не было запросов».

### 6. Итоги сессии — в статус-баре после каждого шага

Статус-бар (`_print_status_bar`) уже печатается после каждой команды и каждого обмена — итоги
сессии (суммарные токены и стоимость) встраиваются туда же: рост расхода виден без отдельной
команды, а `/usage` остаётся развёрнутым отчётом. Данные — из того же `SessionLedger` агента.
Учёт ведётся только по запросам текущей сессии (как счётчик диалогов в статус-баре):
восстановленные из `history.json` обмены не несут метрик использования в накопителе сессии.
Стоимость — компактный формат `${cost:.4f}`; «неизвестно», если стоимость хоть одного запроса
не рассчитана. Команда в подсказку статус-бара не добавляется: по прежнему решению там живут
только `/exit` и `/commands`.

### 7. Расход — в каждой записи истории

Выбор пользователя: каждая запись `history.json` несёт метрики своего обмена —
`{"question", "answer", "usage": {"prompt_tokens", "completion_tokens", "total_tokens",
"cost_usd"}}` (`cost_usd` — null для модели без цены). `HistoryManager.add(question, answer,
usage=None)` — параметр опционален, вызовы без метрик дают запись прежнего вида; загрузка
терпит записи без `usage` (старые файлы читаются как раньше). Итог «всего диалога» — сумма
метрик по записям файла, её агент отдаёт для отчёта `/usage`. Честная граница метода: записи
вытесняются за потолок `HISTORY_LIMIT`, поэтому сумма — это расход *удержанной* истории,
вытесненные записи уносят свой расход; для расхода через рестарты в пределах окна формулировка
точна. `/clear` очищает файл — расход «всего диалога» обнуляется вместе с контекстом, что
согласовано со смыслом очистки (conversation recreation). Альтернатива с накапливающим
итоговым блоком поверх списка отвергнута: меняет форму файла ради числа, которое в рамках
этого приложения сравнительное, а не бухгалтерское.

## Risks / Trade-offs

- Эвристика оценки может заметно расходиться с реальным `prompt_tokens` — снижаем ожидания
  пометкой «≈» и тем, что эталонные числа всегда рядом (метрики последнего запроса).
- Сравнение «диалог, превышающий лимит модели» в демо достигается маленьким
  `TABLETOP_HISTORY_LIMIT` (вытеснение ходов) и reasoning-моделью с минимальным
  `max_words` (пустой ответ) — это клиентски наблюдаемые изломы, а не реальное переполнение
  контекстного окна в 128K+ токенов, которое в живом демо недостижимо.
- Статус-бар становится длиннее; строка по-прежнему однострочная и влезает в стандартную ширину
  терминала при разумных значениях счётчиков (длинные числа токенов — признак того, что пора
  смотреть `/usage`).
- Итог «всего диалога» из записей файла ограничен потолком истории — см. решение 7.
- Снапшоты e2e, где статус-бар или `/commands`-панель видны, потребуют обновления
  (`--snapshot-update`).
