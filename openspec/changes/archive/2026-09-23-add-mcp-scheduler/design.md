## Context

Мотивация — в `proposal.md`, требования — в дельта-спеках изменения. Из существующего кода на решение влияют
три вещи. Первая: MCP-клиент проекта одноразовый — `connect()` и `call_tool()` запускают процесс сервера,
здороваются, делают один вызов и закрывают его; живых соединений между вызовами нет. Вторая: собственный сервер
проекта уже разделён на протокол (`mcp_server/dnd_server.py`) и исполнение вызовов с объявлением схем
(`mcp_server/dnd_tools.py`), а HTTP к внешнему API живёт в `mcp_server/dnd_api.py` с переопределяемым адресом.
Третья: `TabletopAgent` владеет всеми хранилищами и отдаёт терминалу снимки (`context_report()`,
`memory_report()`, `task_report()`), а `ui/tui_app.py` только печатает и никогда не читает файлы состояния сам.

## Goals / Non-Goals

**Goals:**
- Расписание, переживающее перезапуск и работающее без запущенного приложения.
- Сводка, которую выдаёт агент, а печатает терминал — без нарушения границы изоляции.
- Полная изоляция автоматических прогонов: ни сети, ни файлов состояния репозитория.

**Non-Goals:**
- Цепочки заданий, зависимости между ними, календарные выражения вроде cron — период в минутах и отложенный
  старт закрывают задачу дня.
- Обращения к модели из планировщика: задания вызывают инструменты сервера, а не LLM.
- Управление заданиями из отдельной панели терминала: постановка идёт существующими путями — автоматическим
  выбором инструмента и ручным `/tool call`.

## Decisions

**Планировщик живёт в существующем сервере, нового сервера нет.** Альтернатива — отдельный MCP-сервер
`scheduler` в реестре — означала бы, что задание вызывает инструмент *другого* процесса, то есть кросс-серверный
MCP-вызов изнутри сервера, плюс ещё одна запись реестра, ещё один стартовый коннект и ещё одна строка итога при
запуске. Вызов внутри процесса проще и тестируется без сети. Цена: сервер `dnd-rules` перестаёт быть чисто
справочным, и его описание в реестре это отражает.

**Модуль `mcp_server/scheduler.py` отделён от `dnd_tools.py`.** Причина та же, по которой объявление
инструментов уже вынесено из протокола: чистая логика (что просрочено, как сдвигается срок, как строится
агрегат) проверяется юнит-тестами без запуска процесса. Исполнителем задания планировщику передаётся функция
вызова инструмента — тесты подставляют свою и не ходят даже в заглушку HTTP.

**Хранилище — `core/schedule_store.py`, общий для сервера и приложения.** Сервер пишет, приложение читает;
формат — конверт JSON `{"jobs": [...], "runs": [...], "collected": {...}}` с терпимым чтением, как у прочих
сторов. Модуль лежит в `core/`, потому что его читает агент; сервер импортирует его как часть того же
репозитория — так же, как уже импортирует `mcp_server.dnd_api`. SQLite задача допускает, но JSON — конвенция
проекта для состояния, и один файл проще изолировать переменной окружения.

**Гонок за файл нет по построению.** Пишет только серверный процесс (внутри одного вызова
`schedule_run_due`), приложение файл только читает. Запись идёт целиком (сериализация конверта), чтение
повреждённого файла даёт пустой планировщик — то же правило, что у истории и памяти.

**Журнал прогонов ограничен, накопленные данные — нет.** Журнал нужен для отчёта и объявления, поэтому
хранится последними N записями (как журнал переходов задачи). Накопленное заданием — это его результат, его
обрезать нельзя, иначе «встречено впервые» начнёт врать.

**«24/7» держит отдельный процесс `tabletop-scheduler.py`.** Внутри одноразового MCP-клиента цикл жить не
может, а поток внутри приложения не дал бы работы при закрытом приложении. Исполнитель — MCP-клиент: он зовёт
`schedule_run_due` тем же путём, что и любой другой клиент, то есть проверяет протокол, а не внутренние
функции. Режим `--once` существует ради тестов и демонстрации: один прогон, предсказуемое завершение.

**Сводку отдаёт агент, терминал печатает.** Хранилище передаётся в конструктор `TabletopAgent`, курсор
«последний объявленный прогон» живёт на агенте и при старте ставится на последний прогон файла — иначе первая
же реплика вываливала бы всю накопленную историю. Свойство `last_schedule` обновляется по завершении хода, как
`last_compression`/`last_facts`/`last_invariants`; `schedule_report()` — полный снимок для `/schedule`.
Альтернатива (UI сам читает файл) ломает границу, из-за которой все отчёты проекта построены на снимках.

**Имена инструментов остаются вне `core/` и `ui/`.** Приложение не зовёт планировщик по имени: задания ставит
модель автоматическим выбором инструмента или пользователь через `/tool call`, а приложение только читает
хранилище. Действующий инвариант-тест дополняется новыми именами, а не ослабляется.

## Risks / Trade-offs

- Объявление привязано к ходу пользователя: пока он молчит, строка ждёт → осознанная цена решения; настоящий
  push потребовал бы фонового потока, печатающего поверх активного `input()`, что ломает строку ввода readline
  и конфликтует с `rich.Live` во время прогона задачи.
- Исполнитель платит запуск процесса сервера на каждый тик → тик раз в минуту, стоимость запуска ничтожна
  относительно периода; живое соединение потребовало бы фонового событийного цикла и пути остановки.
- Сервер `dnd-rules` теперь имеет побочный эффект (пишет файл) → эффект ограничен одним файлом с
  переопределяемым путём, а тесты и e2e-прогоны этот путь подменяют, как для прочих файлов состояния.
- Расширение каталога инструментов удорожает автоматический выбор инструмента (каталог уходит в промпт) →
  инструментов добавляется немного, а `TOOL_CHOICE_MAX_WORDS` уже поднят под размер каталога; при росте
  каталога это отдельная задача.

## Migration Plan

Изменение аддитивное: без файла планировщика приложение ведёт себя как прежде (строка итога сообщает, что
заданий нет; объявлений нет; `/schedule` печатает пустой отчёт). Откат — снятие команды и хранилища; файл
`schedule.json` остаётся на диске и никем не читается.
