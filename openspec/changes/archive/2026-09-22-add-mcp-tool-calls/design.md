## Context

Мотивация — в `proposal.md`, раздел «Why». Из текущего состояния важно следующее.

`core/mcp_client.py` — синхронная обёртка над асинхронным пакетом `mcp`: соединение поднимается по требованию, выполняет рукопожатие и `tools/list`, после чего закрывается; наружу отдаются снимки, а не живые соединения. `core/config.py` хранит реестр `MCP_SERVERS` описаниями (`MCPServerSpec`), а `TABLETOP_MCP_COMMAND`/`TABLETOP_MCP_ARGS` заменяют весь реестр одной записью — именно так тесты и демо подменяют сервер. Агент (`core/tabletop_agent.py`) — единственное место, решающее, что уходит в модель; терминал рисует отчёты-снимки и внутрь не заглядывает. Вспомогательные запросы (суммаризатор, экстрактор фактов) уже задали образец: свой файл инструкции в `assets/`, разбор ответа на стороне клиента, собственная фаза индикации, расход в общий журнал сессии, сбой не ломает ответ.

Ограничения проекта: ни одно имя инструмента какого-либо сервера не встречается в `core/` и `ui/` (это закреплено тестом); прогон тестов не ходит в сеть; пакет `mcp` требует Python 3.10+.

## Goals / Non-Goals

**Goals:**
- Свой MCP-сервер, покрывающий весь внешний API небольшим числом инструментов с внятными схемами входа.
- Вызов инструмента как обычная операция агента, возвращающая снимок, а не исключение.
- Два пути вызова: явный пользовательский и автоматический по решению модели, с одинаковым результатом на выходе.
- Прогон тестов офлайн, без запуска настоящего сервера и без обращений к публичному API.

**Non-Goals:**
- Долгоживущее соединение с сервером на всю сессию (остаётся одноразовым, как для отчёта).
- Несколько вызовов инструментов подряд в рамках одного вопроса: за вопрос — не больше одного вызова.
- Запись результатов инструмента в историю, долговременную память или рабочую память.
- Поддержка транспортов, кроме stdio.

## Decisions

**Три обобщённых инструмента вместо инструмента на раздел.** Внешний API описывает около двадцати разделов одной и той же формы: список раздела и запись по идентификатору. Инструмент на раздел дал бы около двадцати почти одинаковых описаний, которые грузятся в каждый запрос выбора, раздувая его и одновременно затрудняя выбор: отличить «черту» от «особенности» по описанию труднее, чем передать имя раздела параметром. Три инструмента — перечень разделов, поиск по разделу, запись по идентификатору — покрывают всё то же множество данных при маленькой схеме. Перечень разделов берётся из индекса API, поэтому новый раздел на стороне API появляется у инструментов без правки кода.

**Сервер — отдельный процесс вне `core/` и `ui/`.** Каталог `mcp_server/` содержит серверный скрипт и его HTTP-обращения к внешнему API; приложение знает о нём только команду запуска в записи реестра (интерпретатор проекта плюс путь к скрипту). Это сохраняет правило «имена инструментов приходят от сервера»: сервер — такой же чужой процесс, как `npx`-серверы реестра, просто исходники лежат рядом. Альтернатива — вызывать API напрямую из `core/` — сделала бы задачу дня бессмысленной и нарушила бы существующий тест.

**Базовый адрес API — переменная окружения.** Без этого юнит-тесты сервера ходили бы в публичный API. Переменная читается сервером при старте; тест поднимает локальный HTTP-сервер и передаёт его адрес в окружении процесса. Это тот же приём, что `OPENCODE_API_URL` для модели.

**Валидация аргументов на стороне сервера, до HTTP.** Неизвестный раздел, пустой идентификатор и недопустимая ветка правил отклоняются текстом результата с перечислением допустимых значений. Причина: сообщение об ошибке читает модель — она же выбирала аргументы, и по такому тексту следующий выбор может быть исправлен, тогда как `404` от внешнего API об этом ничего не говорит.

**`call_tool` повторяет схему `connect`.** Одноразовое соединение: запуск процесса, рукопожатие, `tools/call`, закрытие. Держать процессы живыми ради экономии запуска означало бы фоновый поток с событийным циклом и остановку процессов при выходе — отдельная сложность, которую день 16 уже отложил сознательно. Плата известна: каждый вызов платит запуск процесса (десятые доли секунды для своего сервера, заметно больше для `npx`-серверов).

**Автовыбор — отдельный вспомогательный запрос, разбираемый на стороне клиента.** Схема та же, что у экстрактора фактов: инструкция в `assets/`, ответ разбирается поиском первого JSON-объекта, `response_format` не используется (reasoning-модели пула на нём ненадёжны). Ответ «инструмент не нужен» — обычный исход, а не сбой: иначе каждый нетематический вопрос печатал бы ошибку. Альтернатива — вызов инструментов средствами самого API модели (`tools` в запросе) — отвергнута: пул моделей OpenCode Zen неоднороден по поддержке этого поля, а весь проект уже построен на клиентском разборе.

**Результат — отдельное системное сообщение выше диалога, только на текущий вопрос.** Место — рядом с памятью и профилем, до сообщений диалога, с пометкой, что это данные внешнего источника. В историю результат не пишется: файл истории хранит вопрос и ответ, а данные инструмента устаревают и при восстановлении сессии были бы ложным контекстом. Когда вызова не было, состав сообщений не меняется — от этого зависят существующие проверки формы запроса.

**Автовызов включён по умолчанию, выключается командой.** Пользователь просил оба пути. Цена автовызова — один вспомогательный запрос на вопрос; она видна в `/usage`, а `/tool auto off` её убирает. Состояние — сессионное, как выбор модели и настройки ответа: сохранение между запусками в этом проекте всегда было отдельным решением.

**Один вызов на вопрос.** Цепочка вызовов (результат первого инструмента подсказывает второй) потребовала бы цикла с ограничением глубины и бюджета. Для задачи дня достаточно одного, а ограничение делает расход предсказуемым.

## Risks / Trade-offs

- **Публичный API может измениться или стать недоступным** → сервер отдаёт текст ошибки, приложение отвечает без данных инструмента; контрактная проверка против живого API живёт под сетевым маркером и не краснит обычный прогон.
- **Автовыбор ошибается: зовёт инструмент там, где не нужно, или наоборот** → вызов ничего не ломает (результат лишь добавляется к запросу), строка журнала показывает, что именно было вызвано, а `/tool auto off` отключает режим целиком.
- **Лишний запрос на каждый вопрос при включённом автовызове** → расход виден в `/usage`; выключение — одна команда; инструкция выбора короткая, а перечень инструментов мал именно благодаря трём обобщённым инструментам.
- **Запуск процесса на каждый вызов** → для своего сервера это интерпретатор проекта и локальный скрипт; для демонстрации и тестов задержка приемлема, а пересмотр отложен до появления частых вызовов.
- **Результат инструмента — чужой текст в терминале** → печатается с экранированием разметки, как отчёты `/mcp`.
- **Модель может сослаться на данные инструмента как на собственные знания** → инструкция помечает блок как данные внешнего источника, полученные для текущего вопроса; строка журнала показывает пользователю факт вызова.
