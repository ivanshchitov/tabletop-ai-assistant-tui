## Why

Прямая проверка API (для записи демо дня 5) показала: на сложном вопросе, требующем развёрнутого
обоснования, `kimi-k2.6` тратит на генерацию ответа заметно больше 30 секунд (при 1500 токенах —
26.3с и пустой `content`, потому что бюджет ушёл в рассуждение; при 4050 токенах, где ответ уже
непустой, генерация не укладывается даже в 30с). Текущий `REQUEST_TIMEOUT` (30 секунд, по умолчанию)
меньше реального времени генерации для этой пары «сложный вопрос + reasoning-модель», поэтому
клиент обрывает запрос по таймауту и уходит в ретраи с тем же 30-секундным лимитом на каждую
попытку — то есть проблема не устраняется повтором. Пользователь получает ошибку о превышении
времени ожидания там, где модель на деле была готова ответить, просто ей требовалось больше
времени.

## What Changes

- `core/config.REQUEST_TIMEOUT` (переопределяемый через `TABLETOP_REQUEST_TIMEOUT`) поднимается с
  30 до 90 секунд — с запасом покрывает измеренное время генерации (~71с расчётно на 4050 токенов
  при наблюдаемой скорости ~57 токен/с у `kimi-k2.6`).
- Побочный эффект (документируется, не отдельное поведение): при полном исчерпании всех 3 попыток
  таймаута суммарное время до сообщения об ошибке растёт пропорционально (с ~93с до ~273с). Это
  осознанный компромисс — редкие затяжные ответы reasoning-моделей на сложных вопросах не должны
  обрываться ошибкой, если модель реально работает над ответом.

_(нет)_

### Modified Capabilities

- `configuration`: значение по умолчанию `TABLETOP_REQUEST_TIMEOUT` меняется с 30 на 90 секунд.

## Impact

- Код: `core/config.py` (`REQUEST_TIMEOUT`).
- Тесты: `tests/unit/test_config.py` (если там проверяется точное значение по умолчанию — только
  через `os.getenv` без переопределения окружения); прочие тесты, которые задают
  `TABLETOP_REQUEST_TIMEOUT` явно (`tests/e2e/harness.py`, `tests/e2e/test_session.py`), не
  затрагиваются — переопределение через окружение остаётся приоритетным.
- Документация: `README.md`/`CLAUDE.md`, если там фигурирует значение 30 секунд.
