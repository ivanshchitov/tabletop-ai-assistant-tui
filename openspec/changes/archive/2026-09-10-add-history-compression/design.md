# Design: сжатие истории

## Контекст

Сегодня `TabletopAgent` держит плоский стек `_turns` (кап `HISTORY_LIMIT*2` сообщений, старые ходы молча вытесняются) и `history.json` (те же 50 записей, вытеснение). Запрос = system + весь стек + новый user-ход. Задача дня 9: старые ходы сворачиваются моделью в резюме, контекст запроса ограничен потолком токенов, файл хранит всё.

Главный принцип: **компрессия — внутреннее дело агента.** Агент — единственное место, где решается, что уходит в LLM; интерфейс получает только read-only свойства для отчёта. Никакой логики сжатия в `ui/`.

## Состояние агента — третья память

```python
self._turns: List[Dict[str, str]]      # только неотжатые ходы (user/assistant)
self._summary: Optional[str]           # дайджест свёрнутых обменов
self._summary_covers: int              # сколько обменов НАЧАЛА файла покрывает резюме
```

Инвариант: **ходы удаляются из стека только после успешного ответа суммаризатора.** Ошибка API на суммаризаторе — стек и резюме нетронуты, вопрос не отправлен, следующий вопрос повторяет попытку сжатия. Потери хода нет ни на одном пути.

`_summary_covers` считает от **начала** списка записей файла. Файл теперь только растёт (вытеснения нет) — позиции стабильны, счётчик не «плывёт», повторного суммирования покрытого не бывает.

## Чистый модуль компрессии

`core/context_compressor.py` — без HTTP и без rich, по образцу `core/usage.py`:

- `needs_compression(raw_messages: int, threshold: int) -> bool` — порог достигнут;
- `split_for_digest(turns, keep_last: int) -> tuple[list, list]` — пакет сворачиваемых ходов (кратный парам user/assistant) и неотжатый хвост; нечётный хвост не сворачивается;
- `context_messages(system, summary, turns) -> list` — system, затем при наличии одно сообщение-резюме, затем ходы.

Агент оркестрирует: разделение → запрос суммаризатора → при успехе замена резюме и укорочение стека.

## Цикл запроса

1. **Пре-запрос:** если неотжатых сообщений ≥ `compress_after` (настройка сессии, [5..50], дефолт 10) — суммаризатор сворачивает всё, кроме последнего обмена (пара user/assistant всегда остаётся дословной). Сжатие **перед** вопросом, поэтому `_last_result` после `ask()` — метрика ответа, а не суммаризатора; строка токенов после ответа не врёт.
2. Обычный запрос: system + (резюме) + неотжатые ходы + новый user-ход.
3. После ответа — обмен дописывается в `_turns` и в файл, как сейчас; вытеснение за порог — отложенное (пакет при следующем вопросе).

Оценка `stack_tokens_estimate` дополняется резюме; `stack_exchanges` считает неотжатые обмены.

## Запрос суммаризатора

- Системное сообщение — ассет `assets/summary_prompt.md` (по образцу остальных ассетов): сжать переданный обмен, сохранить факты, решения, упомянутые игры; при наличии прежнего резюме — продлить его, а не пересказать с нуля.
- Пользовательское сообщение — прежнее резюме (или явное «пока ничего не свёрнуто») + пакет ходов дословно.
- Параметры: модель сессии, без температуры (клиентский дефолт — правила `/logictask`), `max_tokens = max_tokens_for_words(SUMMARY_MAX_WORDS)`, `SUMMARY_MAX_WORDS = 150` — потолок выхода ограничивает рост резюме.
- Резюме — не диалог: в `history.json` отдельным полем конверта, расход — в накопителе сессии (как у `/logictask`).

## Потолок контекста сессии

`max_session_tokens` — настройка `/settings`, целое [5000..50000], дефолт 20000. Перед вопросом агент оценивает `(system + резюме + неотжатые ходы + новый user-ход)` через `estimate_tokens` (≈, 3 символа/токен). Оценка выше потолка → внеочередное сжатие старейших ходов независимо от порога; если после сворачивания всего, кроме последнего обмена, оценка всё ещё выше (на практике недостижимо: резюме ≤ ~650 ток., вопрос ≤ 2000 симв.) — запрос уходит как есть, ходы не теряются. Реальный `prompt_tokens` ответа подтверждает оценку.

## Хранение: конверт в history.json

```json
{"summary": "текст|null", "summary_covers": 12, "dialogues": [{"question", "answer", "usage"}]}
```

- Записи `dialogues` — прежнего вида; файл старого вида (голый список) читается как конверт с `summary: null`, `summary_covers: 0` — обратная совместимость уже закреплена спекой.
- `HistoryManager` теряет `limit`: ни вытеснения при `add`, ни обрезки при `_load`. Файл растёт неограниченно; цена — полное переписывание файла на каждый обмен (O(n)), та же модель записи, что сегодня; при масштабах проекта неощутимо.
- `/clear` — файл в пустой конверт (обе памяти и резюме одной операцией).
- «Всего диалога» в `/usage` теперь считается по всему файлу — вытесненных записей больше нет, оговорка «расход удержанной истории» исчезает.

## Рестарт и догон

`restore_context()` при конструировании (автоматически, как сейчас):

1. Резюме из конверта — на своё место в собираемом запросе.
2. Сообщения последних `compress_after` обменов файла — неотжатый хвост стека (user — пересбор инструкциями активных настроек, assistant — дословно; прежнее решение спеки сохраняется).
3. Обмены старше хвоста, не покрытые резюме (`len(dialogues) - хвост > summary_covers`), сворачиваются догоняющими запросами по частям при первом вопросе: пакеты ограничены по токенам (оценка суммаризатор-запроса ≤ потолка), каждый пакет вливается в растущее резюме.

Обычный рестарт (резюме актуально) — 0 запросов суммаризатора. После «старого формата» файла — догоняющая суммаризация одним и тем же механизмом триггера, без отдельного кода рестарта.

## Сообщение о сжатии и фаза индикатора

Сжатие НЕ немое: пользователь видит событие. Механика без печатей в агенте:

- **Слушатель фаз:** `TabletopAgent` принимает опционального слушателя фаз при конструировании (умолчание `None` — тихо, для юнит-тестов). Перед запросом суммаризатора агент сигнализирует фазу `COMPRESSION`, перед запросом вопроса — `REQUEST`. Агент не знает ни rich, ни слов: фаза — перечисление в `core/`.
- **Строка о сжатии:** TUI после `ask()` — включая путь ошибки (резюме могло уже уйти, а вопрос упасть) — печатает одну строку в журнал, когда read-only свойство `last_compression` (мета последнего суммаризатора; `None` до первого сжатия) продвинулось относительно напечатанного: «Контекст сжат: N сообщений (M обменов) → резюме».
- **Индикатор по фазе:** TUI маппит фазу на подпись спиннера: `COMPRESSION` → «Суммаризация...», `REQUEST` → «Отправка...».
- **Зачем:** объясняет задержку при срабатывании (два запроса вместо одного) и смену дословных ходов дайджестом.
- **Не в истории:** строка не пишется в `history.json` — при рестарте пропадает, как usage-строки.
- **Без сжатия — без строки:** порог не достигнут — журнал чист.
- **Счётчик диалогов за сессию удалён:** из статус-бара пропадает «Диалогов за сессию: N» — в e2e-ожиданиях маркеры, ждущие счётчик, переезжают на ответы и итоги сессии по токенам (итоги остаются).

## Конфигурация

- Удаляются: `HISTORY_LIMIT`, `TABLETOP_HISTORY_LIMIT` (обе роли капа умерли).
- Добавляются: `DEFAULT_COMPRESS_AFTER = 10` (env `TABLETOP_COMPRESS_AFTER` — сеет дефолт настройки для e2e), `DEFAULT_MAX_SESSION_TOKENS = 20000` (env `TABLETOP_MAX_SESSION_TOKENS`), `SUMMARY_MAX_WORDS = 150`.
- Значения-дефолты настроек живут в `AnswerSettings` (по образцу температуры).

## Решения и границы (осознанные)

- **Выключателя нет** — сжатие всегда активно; порог `/settings` — единственный регулятор. Сравнение «до/после» — внутри одной сессии v0.9: ранние обмены (до пересечения порога — рост `prompt_tokens`) против обменов после срабатывания (плато), плюс расход суммаризатора в `/usage`.
- **Резюме — отдельным сообщением, не в system:** `lru_cache` у `build_system_message` (кеш по формату) не ломается; инструкции формата не смешиваются с дайджестом диалога.
- **Файл хранит всё даже после суммаризации:** сжатие затрагивает только собираемый запрос; на диске обмены дословны, резюме — производная (потеря = перерасчёт). Единственная «потеря» для модели — дословный текст свёрнутых обменов заменён дайджестом.
- **Хвост = последний обмен** — минимальная гарантия связности («а теперь для пяти игроков?»).
- **Догон по частям** — число запросов растёт с объёмом непокрытой истории; разовый расход, виден в `/usage`. Принято.
- `/logictask` не трогается: pinned-параметры, вне стека, историю не меняет — прежние требования остаются в силе.
