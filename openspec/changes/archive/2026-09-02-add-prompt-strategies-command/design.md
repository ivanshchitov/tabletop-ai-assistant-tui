## Context

См. proposal.md. Существующий слой: `DeepseekAPIClient.ask(system_message, user_message)` (два сообщения, ретраи на таймаут), `core/prompts.py` собирает промпты вопрос-ответного режима с учётом `AnswerSettings`. Главный цикл `ui/tui_app.py` распознаёт команды по первому слову (`COMMANDS`), выводит в append-only журнал через `rich`. Stub API в e2e-слое записывает все запросы — тесты смогут проверять фактические промпты, а не только вывод на экране.

## Goals / Non-Goals

**Goals:**
- Четыре стратегии промптинга поверх существующего `ask()` без изменения API-клиента.
- Проверяемость через записанные stub'ом запросы: текст задачи, инструкции, сквозная передача данных.
- Продолжение сессии при ошибке API в середине прогона.

**Non-Goals:**
- Не трогаем вопрос-ответный режим, `AnswerSettings`, историю.
- Не сохраняем результаты прогонов никуда, кроме скроллбека.
- Не делаем стратегию настраиваемой (выбор одной стратегии, другая задача, свой ввод) — фиксированный набор из четырёх.

## Decisions

1. **Новый модуль `core/strategies.py`, а не раздувание `prompts.py`.** Промпты стратегий — отдельная доменная область с собственной константой задачи; `prompts.py` остаётся про форматирование ответов вопрос-ответного режима. Экспортирует: текст задачи, конструкторы промптов для каждого шага, роли трёх экспертов и заголовки стратегий.
2. **Все запросы через существующий `ask(system, user)`.** Альтернатива — метод с произвольным списком сообщений: не нужен, любая стратегия укладывается в пару system/user (сгенерированный промпт стратегии 3 передаётся как system-сообщение второго запроса, задача — как user). Это сохраняет ретраи, проверку ключа и обработку ошибок бесплатно.
3. **Три эксперта — три отдельных запроса.** Альтернатива — один запрос «сыграй трёх экспертов»: дешевле, но решения смешиваются в одном тексте, и теряется паттерн «отдельный запрос = отдельная роль». Отдельные запросы дают чистую структуру «эксперт → решение» и тривиально проверяются stub'ом (ровно 3 запроса с текстом задачи). Плюсы по квоте (1 запрос вместо 3) не перевешивают потерю раздельности решений.
4. **Трое экспертов фиксируются на клиенте, а не запрашиваются у модели.** Альтернатива — первый запрос «предложи трёх экспертов»: демонстрирует модель, проектирующую роли, но добавляет восьмой запрос, вносит недетерминизм в состав панели и требует хрупкого разбора списка ролей. Фиксированный набор (когнитивный психолог, шахматный стратег, специалист по теории игр) детерминирован, проверяется stub'ом дословно и по решению 3 всё равно даёт отдельный запрос на каждого эксперта.
5. **Ошибка прерывает остаток прогона, но не сессию.** Стратегии 3–4 зависят от ответов предыдущих шагов; продолжать с повреждёнными входными данными бессмысленно. Печать ошибки существующим механизмом вопроса-ответа, возврат в главный цикл.
6. **Прогон занимает экран надолго (7 запросов) — вывод через существующие печатающие функции журнала** (`Markdown` + разделители), спиннер на каждый запрос существующий. Анимация печати ответов сохраняется.
7. **Прогон не пишется в историю и не считается диалогом** — по proposal; `run_logictask` не вызывает `history.add`, счётчик не инкрементируется.
8. **Выбор стратегии — интерактивная панель в стиле `/settings`, BREAKING против начального варианта.** Раньше команда прогоняла все четыре стратегии подряд (7 запросов за вызов); по решению пользователя запуск теперь спрашивает, какую стратегию решить, и «все подряд» не предусмотрен. Реализация повторяет слоёную схему `/settings`: чистый редьюсер `ui/logictask_screen.py` (`initial_state` → `apply_key` → выбранная стратегия), тестируемый без терминала; `ui/tui_app.py` только держит `raw_mode()` + `Live` и цикл read-key/redraw. Esc = отмена без запросов. Альтернатива — ввод номера в строке приглашения — дешевле, но ломает единообразие командных экранов и хуже расширяется.

## Risks / Trade-offs

- [7 запросов за один вызов — заметный расход квоты] → задокументировано в proposal; команда ручная, не автоматическая.
- [Прогон не детерминирован по ответам модели] → стратегия 3 двушаговая, но шаги проверяются по записи stub'а; спека проверяет факт трёх запросов с текстом задачи, а не содержание ответов.
- [Панель выбора — ещё один raw-mode экран, риск дублирования кода с `/settings`] → общий каркас (raw_mode + Live + read-key/redraw) остаётся в tui_app, вся логика клавиш — в редьюсере; отказ от «прогона всех подряд» упростил runner до одной стратегии.
- [Долгий прогон (7 × до таймаута)] → существующие ретраи и таймаут; ошибка прерывает остаток прогона.
- [Заголовки стратегий размываются скроллбеком] → заголовки жирным с номером; append-only журнал этого не исправляет, но порядок и различимость обеспечены.

## Migration Plan

Без миграций: новая команда, новый модуль, история и настройки не затронуты. Откат — удаление команды из `COMMANDS` и модуля.
