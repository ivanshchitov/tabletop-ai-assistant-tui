## Context

Мотивация и критерии: `proposal.md`. Контракты: `specs/rules-retrieval/spec.md` и дельта `rules-document-index`.

`core/rules_index.py` хранит два разбиения PDF и нормированные 384-мерные хеш-векторы в SQLite. `search()` сортирует cosine similarity и применяет общий порог 0.10; `embed()` уже расширяет небольшой словарь русских слов. Это лексический эмбеддер, не обученная семантическая модель. Существующий словарь остаётся частью эмбеддера в обоих режимах: отсутствие query rewrite в `baseline` означает отсутствие отдельного этапа изменения вопроса, а не изменение векторизации.

`TabletopAgent.ask()` сейчас получает три фрагмента, строит системный контекст и сохраняет только исходную реплику и ответ. Вспомогательные модельные запросы уже имеют фазы ожидания и общий `SessionLedger`. Терминальный слой работает со снимками агента. Команды `/rules` не обращаются к модели.

## Goals / Non-Goals

**Goals:**

- Отделить получение кандидатов от проверки их соответствия вопросу, не меняя SQLite-схему или сохранённые векторы.
- Сделать отбор и отказ наблюдаемыми, а влияние top-K и порога — воспроизводимым.
- Повторно использовать клиент выбранной модели, учёт расходов и границу «агент отдаёт снимок, TUI отображает».

**Non-Goals:**

- Не вводить отдельный сервис, фоновый процесс, хранилище или общую инфраструктуру цепочек моделей.
- Не изменять стратегии диалоговой памяти, инварианты, очереди задач или MCP-оркестрацию.
- Не обещать калиброванную вероятность правильности по числу, возвращённому моделью.

## Decisions

### 1. Один режим и один набор настроек в сеансе агента

Новый `core/rules_retrieval.py` содержит неизменяемый `RetrievalSettings` с режимом и полями `before`, `after`, `threshold`; агент владеет текущим экземпляром. Командный разбор проверяет итоговую комбинацию атомарно, без нормализации ошибочного ввода: `before` 1..30, `after` 1..10 и не больше `before`, конечный порог 0..1. Значения по умолчанию — `enhanced`, 20, 3, 0.6.

Настройки поиска остаются под `/rules`, а не увеличивают общий экран настроек ответа: они относятся к уже существующему отдельному потоку управления индексом. Нового файла состояния и переменных окружения не требуется. `/clear` очищает диалог по прежнему контракту, но не меняет параметры поиска; новый вопрос заменяет снимок последнего поиска.

### 2. Baseline действительно не выполняет второй этап

Для включённого RAG и готового индекса `baseline` вызывает существующий поиск по исходной реплике с `limit=before` и `minimum_score=-1.0`, затем берёт первые `after`. Это убирает старый фиксированный порог из сравнительного режима, не меняя эмбеддер. `enhanced` использует такой же первый этап, но по переписанному запросу. Используется структурное разбиение, как в текущем вопросном пути.

Существующий `search()` сохраняет API для сравнения разбиений и его прямых потребителей; устаревший непосредственный вызов из `ask()` заменяется новым путём. Оставлять прежний порог 0.10 в `baseline` нельзя: сравнение «без фильтра» иначе скрывало бы действующий фильтр. Перед изменением экспортированных символов в реализации проверяются ссылки доступным LSP.

### 3. Два коротких протокола поверх существующего клиента

Первый вспомогательный запрос: системная инструкция из `assets/rules_query_prompt.md` и исходный вопрос как данные. Ответ — объект `{"query": "..."}` с непустой строкой. Инструкция запрещает отвечать на вопрос, добавлять факты или менять игру и условия; требует английский поисковый запрос. Исходный вопрос никогда не заменяется в истории или запросе ответа.

Второй вспомогательный запрос: инструкция из `assets/rules_rerank_prompt.md`, исходный вопрос, переписанный запрос и до `before` кандидатов. Каждый кандидат получает локальный номер 1..N, название PDF, раздел, chunk_id и полный текст существующего чанка. Ответ — `{"results": [{"id": 1, "score": 0.9, "reason": "..."}, ...]}`. Требуется оценить каждого кандидата ровно один раз; чужая игра и отсутствие подтверждения нужного правила дают низкую оценку. Текст вопроса и фрагментов обозначается как данные, а не новые инструкции. Реранкер ничего не добавляет к тексту источников.

JSON разбирается клиентом по существующей конвенции auxiliary-запросов: первый JSON-объект, без API `response_format` или `stop`. Непустой `query`, корректная структура списка, полное покрытие номеров без дублей и числовые конечные оценки 0..1 проверяются до отбора; логическое значение не считается числом. Пояснение должно быть строкой. Неизвестный номер, пропуск или неверная оценка делают весь результат непригодным, вместо молчаливого выбора удобной части.

Оба запроса используют модель сеанса и технические бюджеты из `core/config.py` через существующий `max_tokens_for_words()`, с достаточным запасом для reasoning-моделей и результата по 30 кандидатам; температура остаётся клиентской по конвенции auxiliary-запросов. Начальные бюджеты: 500 слов для rewrite и 2000 для оценок, не пользовательское ограничение объёма ответа. Проверка на живой модели определяет достаточность бюджетов без подмены пустого результата успехом.

Альтернативы: только cosine-порог не отличает чужие правила с высокой похожестью; локальные эвристики потребовали бы ручных словарей игр и формулировок; cross-encoder добавил бы модель и зависимость. Выбранная модель уже доступна через клиент проекта, поэтому добавляется протокол, а не новый провайдер.

### 4. Детерминированный отбор после оценок

Чистые функции нового модуля строят запросы, разбирают ответы и формируют решения по кандидатам. Допуск — `score >= threshold`, сортировка стабильная по убыванию оценки, конечный срез — `after`. Исключение имеет отдельную причину: ниже порога или за конечным top-K. В снимке сохраняются обе оценки — cosine первого этапа и релевантность второго; они не смешиваются в одно число.

`SearchResult` и его данные остаются исходным представлением переданного источника. Снимок `RetrievalReport` содержит исходный вопрос, поисковый запрос, неизменяемые настройки на момент поиска, решения по кандидатам, итоговые `SearchResult`, статус и ошибку. Решения ссылаются на существующие объекты кандидатов, не копируют их текст. TUI получает снимок через агент и не читает его внутренние поля или SQLite самостоятельно для нового отчёта.

### 5. Ошибка не открывает обход второго этапа

Проверка выключенного RAG и готовности индекса выполняется до переписывания. При выключенном RAG, отсутствующем индексе или отсутствии кандидатов не выполняются ненужные дальнейшие запросы; старый контекст и источники очищаются перед новым ответом.

При ошибке API, пустом или непригодном ответе rewrite/rerank снимок сообщает конкретный неуспешный этап. Итоговый ответ идёт обычным путём без RAG. Не используется скрытый возврат к исходным кандидатам: это выдало бы обход фильтра за успешный улучшенный поиск. Новых повторных запросов, кроме существующих HTTP-retry клиента, нет. Ошибка самого итогового ответа по-прежнему распространяется как `APIError` и не сохраняет успешный обмен.

Успешный HTTP-ответ auxiliary-запроса учитывается в ledger даже при непригодном содержимом — токены реально потрачены. Фазы `RULES_REWRITE` и `RULES_RERANK` задают подписи ожидания. После итогового ответа `last_result` относится к нему; общий `/usage` включает всю цепочку.

### 6. Отчёт без повторного поиска

`/rules` показывает текущие параметры. `/rules retrieval baseline|enhanced` переключает режим, `/rules tune` атомарно меняет параметры, `/rules trace` только отображает снимок последнего вопроса. Отчёт показывает для всех реально найденных кандидатов источник, раздел, chunk_id, cosine, модельную оценку при наличии и итоговую причину. Переписанный запрос и диагностические строки экранируются через `rich.markup.escape`, как прочий внешний текст.

Старый `/rules compare <вопрос>` сохраняет сравнение разбиений, не вызывает модель и не превращается в сравнение генераций. Отчёты, параметры и диагностика не попадают в `history.json`.

### 7. Сравнение — измерение, не самопроверка реранкера

`docs/rag-reranking-questions.md` фиксирует три вопроса: русский о стоимости дороги CATAN, о выборе открытого локомотива Ticket to Ride и о подсчёте очков Azul вне корпуса. Для первых двух задаются ожидаемый PDF и факты; для третьего ожидается отсутствие релевантного PDF, а правильность ответа из знаний модели оценивается отдельно. Ожидания подтверждаются текстом PDF до живого прогона.

Одинаковая модель и настройки ответа, включённый RAG, инструменты отключены для обоих прогонов. Для независимых результатов каждый контрольный вопрос начинается с чистого диалога в обоих режимах. Сначала выполняются все вопросы в `baseline`, затем те же вопросы в `enhanced`. Таблица показывает число релевантных переданных фрагментов из общего числа, подтверждение ключевых фактов контекстом и правильность этих фактов; при пустом контексте релевантность отмечается как «нет контекста», а не 100%.

Автоматизация живой демонстрации в `videos/tmp/` использует существующий подход дня 22: собственное окно терминала по id, изолированные пути состояния, ожидание отрисованных маркеров и строки метрик, остановка записи в `finally`. Числа расходов читаются из метрик и снимков текущего прогона. Проверка утверждений и кадров обязательна; наличие красивого отчёта не считается доказательством улучшения.

## Risks / Trade-offs

- [Дополнительная задержка и стоимость двух запросов] → явные фазы, ledger и `baseline` для сравнения; отсутствующий индекс не тратит запросы.
- [Оценки модели некалиброваны и недетерминированы] → порог 0.6 является стартовой настройкой, не вероятностью; тестируется детерминированная обработка оценок, а качество проверяется на живых ответах и PDF.
- [Переписывание может изменить смысл] → исходный вопрос остаётся в реранкере и ответе, обе формулировки доступны пользователю; нет обещания программно доказать смысловую эквивалентность.
- [Первый top-K не содержит нужного чанка] → второй этап не создаёт источник; количество кандидатов настраивается, отсутствие результата честно показывается.
- [Полный набор до 30 чанков увеличивает prompt] → ограничены число кандидатов и уже существующий размер чанка; не вводится молчаливое обрезание текста, которое скрывало бы подтверждение правила.
- [Ответ из знаний модели верен даже без контекста] → метрики правильности и опоры на источники разделены.
- [Изменение режима по умолчанию меняет контракт существующих тестов] → существующие интеграционные проверки RAG получают ответы rewrite/rerank или явно выбирают `baseline`, когда проверяют старый одношаговый режим; тесты не привязываются к новым формулировкам справки.

## Migration Plan

Индекс совместим: переиндексация не нужна. После внедрения новый сеанс использует `enhanced`; `/rules retrieval baseline` позволяет выбрать простой поиск, `/rules mode off` полностью выключает RAG. Все вопросные вызовы мигрируют на один новый путь, без параллельной старой реализации. Основные спецификации изменяются только штатной архивацией после доказательства работы. Публикация, слияние и тег `v0.23` требуют отдельных подтверждений пользователя.
