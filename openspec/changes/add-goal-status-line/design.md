# Дизайн: цель диалога в статус-баре

## Контекст

Рабочая память задачи живёт в `TabletopAgent._working` (ключи — категории `цель`/`ограничения`), заполняется детерминированной таблицей правил `memory_layers.RULES` и переживает перезапуск через конверт `history.json`. Статус-бар собирается в `ui/tui_app.py::_status_bar_line` и уже показывает необязательные части по одному принципу: профиль — только непустой, задача — только при непустой очереди. Цель идёт туда же третьей необязательной частью.

## Решения

- **Источник — `memory_report()`, не `_working`.** Граница изоляции отчётов (как `profile_report()`/`task_report()` рядом): терминал читает снимок, а не поля агента. Запись цели ищется по ключу `memory_layers.CATEGORY_GOAL` среди `report.working`.
- **Показ только при непустой цели.** Пустая рабочая память — раскладка статус-бара прежняя; несколько e2e-тестов экрана зависят от этой раскладки.
- **Позиция — после блока задачи, перед форматом.** Цель диалога и задача очереди — соседние по смыслу части («память задачи»).
- **Экранирование обязательно.** Значение цели — пользовательский текст; как имя профиля, печатается через `rich.markup.escape`, иначе `[/dim]` в тексте цели поднимает `MarkupError`.
- **Ограничения не показываются.** Строка статус-бара одна; ограничения остаются в `/memory`. Цель — главный признак «памяти задачи» в кадре.

## Альтернативы

- Отдельная команда `/goal` — отклонено: цель уже пишется правилами маршрутизации и `/memory goal`; новая команда ничего не добавляет.
- Показывать и ограничения — отклонено: строка станет двухэтажной; отчёт `/memory` уже покрывает.

## Риски

- Цель длинная → строка статус-бара переносится. Принимаем: лимит значения уже есть (`config.MEMORY_VALUE_MAX_CHARS`), а перенос dim-строки не ломает журнал.
