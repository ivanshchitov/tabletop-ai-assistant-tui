## Purpose

Сохранение диалогов между запусками в единственном файле `history.json`: загрузка и воспроизведение при старте, немедленное сохранение каждого успешного обмена, ограничение объёма и очистка командой `/clear`.

## Requirements

### Requirement: Расположение и переопределение пути
История SHALL храниться в файле `history.json` в корне репозитория. Путь SHALL переопределяться переменной окружения `TABLETOP_HISTORY_FILE` — так, чтобы путь по умолчанию выводился из расположения кода, а не из рабочего каталога процесса: ни один запуск (включая тестовые) не должен писать в реальный файл без явного переопределения.

#### Scenario: Переопределение пути
- **WHEN** задана переменная `TABLETOP_HISTORY_FILE`, указывающая на другой файл
- **THEN** история читается и пишется в указанный файл, а реальный `history.json` не трогается

### Requirement: Загрузка и воспроизведение при старте
История SHALL загружаться один раз при запуске. Если она непуста, прошлые обмены SHALL воспроизводиться в журнал главного экрана в исходном виде (вопрос, ответ, разделитель) до первого приглашения ввода; если пуста — показывается приветственное сообщение.

#### Scenario: Непустая история
- **WHEN** приложение запускается с сохранёнными диалогами
- **THEN** все сохранённые обмены видны в журнале, приветствие не показывается

#### Scenario: Пустая история
- **WHEN** приложение запускается впервые (файла истории нет)
- **THEN** показывается приветственное сообщение, а не пустой реплей

### Requirement: Немедленное сохранение каждого обмена
Каждый успешный обмен (вопрос и полученный ответ) SHALL добавляться в историю и сразу же записываться на диск — сбой приложения после ответа не должен терять историю. Неудачные запросы (ошибка API) SHALL NOT попадать в историю.

#### Scenario: Обмен сохранён
- **WHEN** модель ответила на вопрос
- **THEN** пара «вопрос–ответ» немедленно появляется в файле истории

#### Scenario: Ошибка API не сохраняется
- **WHEN** запрос к модели завершился ошибкой
- **THEN** файл истории не изменяется

### Requirement: Очистка командой /clear
Команда `/clear` SHALL очищать краткосрочную и рабочую память и в памяти, и в файле, включая память стратегии —
сжатое резюме и блок фактов: файл становится конвертом с `summary: null`, `summary_covers: 0`, `facts: {}`,
`working: {}` и пустым `dialogues`, о чём сообщается пользователю. Долговременная память — отдельный слой со своим
файлом — очисткой SHALL NOT затрагиваться. Последующий запуск SHALL начинаться с пустой историей без резюме, без
фактов и без данных текущей задачи, но с прежними записями долговременной памяти.

#### Scenario: Очистка
- **WHEN** пользователь выполняет `/clear` при непустой истории
- **THEN** файл — пустой конверт, выводится подтверждение

#### Scenario: Очистка забирает факты
- **WHEN** перед очисткой на стратегии фактов был накоплен непустой блок фактов
- **THEN** после очистки файл не содержит фактов, а следующий вопрос уходит с пустым блоком

#### Scenario: Очистка забирает рабочую память
- **WHEN** перед очисткой в рабочей памяти были цель задачи и ограничения
- **THEN** после очистки файл не содержит блока рабочей памяти, а следующий вопрос уходит без данных текущей задачи

#### Scenario: Очистка оставляет долговременную память
- **WHEN** перед очисткой был непустой файл долговременной памяти
- **THEN** после очистки файл долговременной памяти не изменился

### Requirement: Устойчивость к повреждённому хранилищу
Отсутствующий файл, нечитаемый JSON или ошибка записи SHALL NOT приводить к падению приложения: битый файл читается как пустая история, ошибка записи игнорируется, работа продолжается.

#### Scenario: Битый файл истории
- **WHEN** `history.json` содержит невалидный JSON
- **THEN** приложение стартует с пустой историей, без ошибки

#### Scenario: Ошибка записи не фатальна
- **WHEN** запись истории на диск не удалась (например, каталог недоступен)
- **THEN** приложение продолжает работу, диалог не прерывается

### Requirement: Реплей истории восстанавливает контекст агента
Воспроизведение истории при старте SHALL засеивать контекст агента: сохранённое резюме SHALL занимать своё место
в собираемом запросе, сохранённый блок фактов SHALL восстанавливаться, сообщения последних `compress_after`
сохранённых обменов SHALL становиться ходами `user`/`assistant` стека (ход `user` — инструкциями активных
настроек ответа, ход `assistant` — дословно). Обмены файла старше хвоста, не покрытые резюме, SHALL сворачиваться
суммаризатором по частям при первом вопросе — только при активной стратегии сжатого резюме. Глубина контекста
SHALL определяться стратегией управления контекстом и потолком токенов сессии, а не лимитом записей файла.

#### Scenario: Первый вопрос после рестарта несёт прошлый обмен
- **WHEN** приложение перезапущено с непустой `history.json` и пользователь задаёт первый вопрос
- **THEN** запрос содержит system, резюме (если есть), восстановленный хвост и новый user-ход

#### Scenario: Рестарт с пустой историей
- **WHEN** приложение запущено с пустой или отсутствующей историей
- **THEN** стек и резюме пусты, первый вопрос отправляется без ходов, как при первом запуске

#### Scenario: Очистка после рестарта
- **WHEN** после рестарта с непустой историей выполнена команда `/clear` и задан новый вопрос
- **THEN** файл, стек и резюме пусты, запрос содержит system и один user-ход

#### Scenario: Рестарт восстанавливает факты
- **WHEN** приложение перезапущено с историей, содержащей блок фактов, и активна стратегия фактов
- **THEN** первый вопрос уходит с восстановленным блоком фактов

### Requirement: Метрики использования в записях истории
Каждый успешно сохранённый обмен SHALL хранить метрики использования своего запроса:
входные, выходные и суммарные токены и стоимость (null, если стоимость не рассчитана).
Записи без метрик (старый формат файла) SHALL читаться как обычные обмены без метрик.
Итог расхода всей сохранённой истории SHALL вычисляться суммированием метрик по записям;
из-за вытеснения записей за лимит итог отражает расход удержанной истории. `/clear`
обнуляет эти итоги вместе с историей.

#### Scenario: Обмен сохраняется с метриками
- **WHEN** вопрос успешно отвечен моделью
- **THEN** запись истории содержит блок метрик с токенами и стоимостью этого запроса

#### Scenario: Файл старого формата читается
- **WHEN** в файле есть записи без блока метрик
- **THEN** они загружаются как обычные обмены, ошибок нет, итог расхода их не учитывает

#### Scenario: Вытесненная запись уносит расход
- **WHEN** запись вытеснена за лимит истории
- **THEN** её метрики больше не входят в итог расхода сохранённой истории

### Requirement: Конверт формата истории
Файл истории SHALL храниться как конверт `{"summary": <строка|null>, "summary_covers": <целое>, "facts":
{<ключ>: <строка>}, "working": {<ключ>: <строка>}, "dialogues": [<записи>]}`. Записи `dialogues` — прежнего
вида: вопрос, ответ и опциональный блок метрик. Блок `working` — рабочая память агента: данные текущей задачи
(цель, ограничения). Файл прежнего вида — голый список записей — SHALL читаться как конверт с `summary: null`,
`summary_covers: 0` и пустыми `facts` и `working`. Новая запись SHALL дописываться в `dialogues` без вытеснения
прежних; `summary` и `summary_covers` SHALL обновляться при каждом сжатии контекста агента, `facts` — при каждом
успешном обновлении блока фактов, `working` — при каждой записи в рабочую память. `summary_covers` SHALL считать
записи от начала списка: файл только растёт, счётчик стабилен. Ветки диалога и записи долговременной памяти в файле
SHALL NOT храниться: `dialogues` — плоский список обменов независимо от веток, а долговременная память живёт в
собственном файле. Устойчивость прежняя: отсутствующий файл или нечитаемый JSON читаются как пустая история без
резюме, фактов и данных текущей задачи, ошибка записи не фатальна.

#### Scenario: Файл старого формата читается
- **WHEN** файл содержит голый список записей без конверта
- **THEN** записи загружаются как обмены, резюме, факты и рабочая память отсутствуют, приложение работает

#### Scenario: Новый файл пишется конвертом
- **WHEN** выполнен успешный обмен, сжатие контекста, обновление фактов или запись в рабочую память
- **THEN** файл — конверт с `dialogues`, `summary`, `summary_covers`, `facts` и `working`, прежние записи не вытеснены

#### Scenario: Битый файл
- **WHEN** файл содержит невалидный JSON
- **THEN** приложение стартует с пустой историей без резюме, фактов и данных текущей задачи, без ошибки

#### Scenario: Конверт без блока фактов
- **WHEN** файл содержит `summary` и `dialogues`, но поля `facts` нет
- **THEN** история загружается, блок фактов считается пустым, ошибок нет

#### Scenario: Конверт без блока рабочей памяти
- **WHEN** файл содержит `summary`, `facts` и `dialogues`, но поля `working` нет
- **THEN** история загружается, рабочая память считается пустой, ошибок нет

#### Scenario: Рабочая память восстанавливается из конверта
- **WHEN** файл содержит непустой блок `working`, и агент создан на этом файле
- **THEN** снимок памяти показывает записи рабочей памяти, а следующий вопрос уходит с данными текущей задачи
