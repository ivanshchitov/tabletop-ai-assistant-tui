## Purpose

Взаимодействие с OpenAI-совместимым эндпоинтом OpenCode Zen (модель `deepseek-v4-flash`): форма запроса, технические потолки, политика повторов и обработка ошибок. Клиент изолирован от терминала и тестируется подменой HTTP-слоя.

## Requirements

### Requirement: Форма запроса к модели
Запрос SHALL выполняться методом POST на эндпоинт chat/completions (по умолчанию `https://opencode.ai/zen/v1/chat/completions`) с заголовком `Authorization: Bearer <ключ>` и JSON-телом, содержащим: модель `deepseek-v4-flash`, два сообщения (system — системное сообщение, user — пользовательский промпт), температуру из активной настройки сессии (по умолчанию 0.7) и `max_tokens`. Других сообщений (вся накопленная история) в запросе быть не должно — история ведётся только для отображения.

#### Scenario: Успешный вопрос
- **WHEN** пользователь задаёт вопрос с активными настройками
- **THEN** к API уходит POST-запрос с моделью deepseek-v4-flash, системным и пользовательским сообщениями, температурой из настройки сессии (по умолчанию 0.7) и max_tokens

#### Scenario: История не отправляется
- **WHEN** задан третий вопрос за сессию
- **THEN** запрос содержит ровно два сообщения (system, user), а не накопленную историю

#### Scenario: Температура из настройки
- **WHEN** пользователь установил температуру 1.2 и отправляет вопрос
- **THEN** тело запроса содержит temperature = 1.2

### Requirement: max_tokens — технический потолок, а не рычаг управления длиной
Значение `max_tokens` SHALL вычисляться из настройки объёма по щедрой формуле (количество слов × 4 + 50) и служит только техническим потолком, чтобы генерация не обрывалась раньше, чем модель сама уложится в инструкцию объёма. Реальное управление длиной ответа — только инструкция в промпте.

#### Scenario: Значение по умолчанию
- **WHEN** объём ответа равен 200 слов
- **THEN** запрос содержит max_tokens = 850

#### Scenario: Рост объёма
- **WHEN** пользователь увеличивает объём с 100 до 200 слов
- **THEN** max_tokens в запросе увеличивается соответственно (450 → 850)

### Requirement: Запрет параметра stop
Тело запроса SHALL NOT содержать параметр `stop`. Модель — reasoning-модель: перед `content` она возвращает отдельное поле рассуждений, и жёсткий stop, совпавший в рассуждениях, обрывает ответ с пустым `content`. Любое управление остановкой — только через инструкции промпта.

#### Scenario: Тело запроса без stop
- **WHEN** отправляется любой вопрос
- **THEN** JSON-тело запроса не содержит ключа `stop`

### Requirement: Валидация ключа до запроса
Ключ SHALL считаться пригодным, только если он непустой и состоит из ASCII-символов (HTTP-заголовки кодируются latin-1, кириллица в ключе — типичная опечатка русской раскладки). При непригодном ключе ошибка SHALL сообщаться до выполнения HTTP-запроса понятным сообщением про раскладку клавиатуры, а не падением на кодировании заголовка.

#### Scenario: Кириллический ключ
- **WHEN** ключ набран в русской раскладке
- **THEN** запрос не отправляется, пользователь видит сообщение о недопустимых символах

#### Scenario: Валидный ключ
- **WHEN** ключ непустой и ASCII
- **THEN** запрос отправляется с этим ключом в заголовке Authorization

### Requirement: Политика повторов
При таймауте запроса клиент SHALL повторять попытку до 3 раз включительно с экспоненциальной паузой между попытками; после исчерпания — понятное сообщение о превышении времени ожидания. При ошибке соединения повторы SHALL NOT выполняться (персистентная сетевая проблема, а не переходный сбой): сразу сообщение о проверке интернет-соединения.

#### Scenario: Один таймаут и успех
- **WHEN** первая попытка истекает по таймауту, вторая завершается ответом
- **THEN** пользователь получает ответ, всего выполнено 2 попытки

#### Scenario: Все попытки истекли
- **WHEN** все 3 попытки истекают по таймауту
- **THEN** пользователь видит сообщение о превышении времени ожидания

#### Scenario: Ошибка соединения без повторов
- **WHEN** сервер недоступен (ошибка соединения)
- **THEN** выполняется ровно одна попытка, пользователь видит сообщение о соединении

### Requirement: Обработка ответов и ошибок API
Ответ модели SHALL извлекаться из первого варианта ответа API и передаваться приложению без обрамляющих пробелов. Ответ с HTTP-статусом 401 SHALL превращаться в сообщение о неверном API-ключе; прочие HTTP-ошибки и нечитаемые ответы (битый JSON, неожидаемая структура) — в понятные русскоязычные сообщения об ошибке. Все ошибки API SHALL выбрасываться единым типом ошибки, который интерфейс показывает пользователю без traceback.

#### Scenario: Неверный ключ
- **WHEN** API отвечает статусом 401
- **THEN** пользователь видит сообщение о неверном API-ключе

#### Scenario: Серверная ошибка
- **WHEN** API отвечает статусом 5xx
- **THEN** пользователь видит сообщение об ошибке API, а не traceback

#### Scenario: Некорректный ответ
- **WHEN** API вернул валидный HTTP-ответ без ожидаемой структуры (нет вариантов ответа)
- **THEN** пользователь видит сообщение о некорректном ответе API
